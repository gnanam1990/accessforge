# Module 15 — Matched candidate verification

**Scope built:** the verification record and every gate that refuses to call a repair verified.
**Not built:** the complete candidate-to-reader dispatch and therefore any actual verified repair.
Module 14 now builds retained owned reference candidates and records protected backend regression
results (see `14-candidate-build.md`); these are not yet bound to a matched actual-reader run.
**Matched-reader runtime proof is BLOCKED.**

## The design claim

`conclude_verification` takes no verdict argument **and no evidence argument**. Adversarial review
found the second half: the previous version accepted a `CandidateEvidence` the caller filled in --
baseline outcome, candidate outcome, producer watermarks, regression result -- and derived VERIFIED
from it. Anything that could call it could therefore assert a repair had been verified without a run
having happened, and the only thing between a fabricated pair and a VERIFIED record was the caller's
honesty.

Now it takes identifiers. Every gate reads rows this product wrote: `run.status` and `run.outcome`
for both runs, `sealed_manifest` for both identities, `producer_stream.closed_at_sequence` for the
watermarks. `TrustedEvidence` has no constructor a caller reaches.

**In this deployment the conclusion can never be VERIFIED.** Nothing durably attests protected
functional regressions for the candidate run. The newer module 14 primitive builds and runs
protected HTTP/database checks on captured owned-reference wheels, but no durable result is yet
bound to a candidate run/lease/epoch, so this gate remains unmet. An in-memory result or test report
cannot substitute for that record. That is asserted by
`test_verified_is_unreachable_while_no_runner_attests_regressions`, which satisfies every other gate
and still gets INCONCLUSIVE. Reaching VERIFIED requires trusted persisted regression results and a
complete actual matched reader pair, not a different argument. Its parameters are `conn`, `workspace_id`,
`verification_id`, `candidate_run_id`, `permitted_differences` and `now` — asserted by a test that reads the signature, so a future
change adding a `conclusion=` parameter fails there rather than in review.

That is the whole mechanism behind CONTRACTS' rule that "human review cannot convert an INCONCLUSIVE
candidate to VERIFIED". There is no route that writes a conclusion; a contract test reads the live
OpenAPI schema and fails if any request body anywhere mentions `conclusion` or `verdict`. The
conclusion is derived from recorded evidence or it does not exist.

## Acting under an approval, in both places

`open_verification` rechecks the `PATCH_APPLY` approval before it inserts anything or moves the patch
to BUILDING, using the same check a dispatch makes. Previously it looked only at the status, so a
revoked, expired or superseded approval still produced a verification record and moved the patch -- a
candidate begun under an authorization that no longer existed, with a row afterwards implying somebody
had granted one.

The source-tree comparison that `assert_dispatchable` also makes is deliberately **absent** here: no
candidate source can be observed from this deployment, and inventing a digest to compare would be
worse than comparing nothing. The route says so in its `runtimeProof` field.

Concluding is atomic. The state and the revision are predicates in the `UPDATE` that writes the
verdict, and a row count other than one raises: two callers racing cannot both succeed, and the first
verdict stands rather than whichever finished second.

`permitted_differences` are validated before anything is written. Each needs a non-empty string
`field` and a present `candidate` key, distinguished from a null one by a sentinel -- `dict.get`
collapses absent and null, and `str(None)` is the string `"None"`, so an entry that forgot to say what
the candidate value was could waive a drift whose candidate value happened to be absent.

## What VERIFIED requires

All of it, together:

1. A candidate run that actually ran.
2. A baseline whose outcome is `FAIL` — a repair can only be established against a failure that was
   established first, or a passing candidate proves the behaviour was never broken (INV-02).
3. A candidate outcome of `PASS`. Anything else, `INCONCLUSIVE` included, leaves it unestablished.
4. Closing watermarks from every required producer. A producer that stopped without closing leaves a
   tail nobody can account for, and a contiguous chain does not cover that (INV-06).
5. Protected functional regressions passing: validation, authorization, successful submission, failed
   input handling. A patch that fixes an announcement by removing the thing announced passes the
   accessibility assertion and breaks the application.
6. Frozen assertions and observer contract unchanged between the two runs (INV-03).
7. Identities differing only by the approved patch and differences explicitly recorded as permitted
   (INV-04). Unexplained drift in browser, reader, evaluator, fixture or locale disqualifies the pair.

**Missing evidence is INCONCLUSIVE, not NOT_ESTABLISHED.** A run that produced no verdict has not
shown the repair failed — it has shown nothing. Conflating them would let an infrastructure problem
read as a rejected repair, and the next person would go looking for a better patch instead of a
working runner.

**A failed verification removes nothing.** The finding keeps its status and all its evidence; a test
asserts the finding is still `REPRODUCED` afterwards. The opposite — a failed repair attempt quietly
downgrading the finding it failed to fix — would make trying a patch a way to make a defect go away.

Every attempt is listed, never a selected one. That is the difference between a verification and a
search for a favourable result.

## Verification of this module

24 integration tests against real PostgreSQL 17, including one parameterised case per gate: a single
test asserting "not verified" would pass if only one gate worked.

Mutation checks on the dispatch recheck, the base-digest comparison, the candidate-outcome gate, the
drift check, the lifecycle transition table, the conclusion-is-frozen guard, and two schema
constraints (`verified_requires_a_candidate`, forced RLS). All caught; files restored byte-identically.

## Limitations — read these before quoting anything

- **No complete matched actual-reader candidate has established a verified repair.** Module 14's
  real captured-wheel builds and durable backend regressions are narrower proof. The fabricated
  evidence helper is gone; `VERIFIED` remains unreachable without trusted candidate-run linkage
  and the complete reader/observer evidence.
- The module prompt's acceptance gate — reproduce the baseline on the reference application's real
  backend, apply the approved patch, rerun under the pinned VoiceOver profile — **has not been run**.
  Per its own stop condition, runtime proof is marked BLOCKED and no repair is marked VERIFIED.
- `POST /patches/{id}/verifications` says so in its response: `runtimeProof` states that no candidate
  can be produced here.
- ~~The gates trust what the caller reports about a candidate run.~~ **Closed.** They read recorded
  rows. Protected functional regressions now have build-bound records, but not a trusted binding
  to the exact candidate run/lease/epoch. `_regression_attestation` remains False until the complete
  dispatch and evidence path exists; selecting any PASSED build or same-workspace run is insufficient.
- Human review remains a separate dependency. `VERIFIED → REVIEW_ACCEPTED` is in the lifecycle; no
  route drives it yet, and `RESOLVED` on a finding still requires review that module 16 owns.

### Live binding continuation (draft PR #37)

Migration 0032 now binds prepared candidate run/seal/fixture/source/build/environment identities to
the live regression endpoint and first desktop lease/epoch. Conclusion uses that exact run and
the narrowly derived environment-only comparison allowance; caller-supplied replacement IDs or
widened differences are refused. Frozen fixture creation-time contracts have no historical
backfill. These bindings are necessary inputs, not proof that a reader ran: independent RUN_EFFECTS
transport authorization, actual canonical reader/observer producers and finalization remain absent.
Bound-session POST and `_regression_attestation` therefore remain fail closed. Actual-runtime tests
use synthetic baseline and desktop metadata and cannot satisfy this module's VoiceOver gate.

Migration 0033 closes a separate identity gap: new candidates require complete schema-valid
RunManifest payloads including fresh run/authorization IDs, journey version, effects, budgets and
expiry. Old seals retain only their original input fingerprints with NULL canonical payload;
missing historical execution authority is never backfilled. A reserved authorization ID is not
an approval. The actual execution/reader/observer acceptance requirements above remain unmet.

The public seal API now also supports these full manifests through its explicit `execution`
object, and a project/workspace-scoped GET exposes the exact immutable payload for human review.
Legacy fingerprints are labeled separately and cannot acquire missing historical authority.
Canonical admission rejects expired execution scope and revoked environments before quota charge.
This closes the public manifest-review input gap, not the remaining RUN_EFFECTS approval or
actual-reader/controller/observer acceptance gates.

Manual consent now has separate RUN_APPROVE-protected issue/inspect/revoke routes bound to the
immutable full seal, its reserved authorization ID and fixed target revision. A trusted manual
pre-dispatch gate reloads that decision and shares the runner/lease/profile/preflight checks;
restore irreversibly invalidates old exact consent. These are implemented control-plane inputs,
not a completed controller integration or actual-reader run. Bound-session POST and verification
remain closed until canonical execution, per-action journaling/effect checks, observer closure and
stop/finalization are connected and proven. No fabricated standing grant substitutes for E0 consent.

The one-shot manual controller now commits exact attempt/lease identity before its trusted handoff
port and fences ambiguous delivery without retry. Its default actual-reader transport is still
unavailable; see [handoff 07](07.md#manual-controller-continuation). It does not open candidate POST,
produce observer/reader evidence, or satisfy any VERIFIED repair gate.
