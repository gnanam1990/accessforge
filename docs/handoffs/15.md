# Module 15 — Matched candidate verification

**Scope built:** the verification record and every gate that refuses to call a repair verified.
**Not built:** the candidate build, the rerun through a real reader, and therefore any actual verified
repair. **Runtime proof is BLOCKED.** That is the honest state and the rest of this document depends
on it.

## The design claim

`conclude_verification` takes no verdict argument **and no evidence argument**. Adversarial review
found the second half: the previous version accepted a `CandidateEvidence` the caller filled in --
baseline outcome, candidate outcome, producer watermarks, regression result -- and derived VERIFIED
from it. Anything that could call it could therefore assert a repair had been verified without a run
having happened, and the only thing between a fabricated pair and a VERIFIED record was the caller's
honesty.

Now it takes identifiers. Every gate reads rows this product wrote: `run.status` and `run.outcome`
for both runs, `sealed_manifest` for both identities, `producer_stream.closed_at_sequence` for the
watermarks. `TrustedEvidence` has no constructor a caller reaches.

**In this deployment the conclusion can never be VERIFIED.** Nothing attests protected functional
regressions -- no runner executes the application's protected tests and no table records the result
-- so that gate is permanently unmet, and an unknown gate is an unmet gate. That is asserted by
`test_verified_is_unreachable_while_no_runner_attests_regressions`, which satisfies every other gate
and still gets INCONCLUSIVE. Reaching VERIFIED requires a runner, not a different argument. Its parameters are `conn`, `workspace_id`,
`verification_id`, `evidence` and `now` — asserted by a test that reads the signature, so a future
change adding a `conclusion=` parameter fails there rather than in review.

That is the whole mechanism behind CONTRACTS' rule that "human review cannot convert an INCONCLUSIVE
candidate to VERIFIED". There is no route that writes a conclusion; a contract test reads the live
OpenAPI schema and fails if any request body anywhere mentions `conclusion` or `verdict`. The
conclusion is derived from recorded evidence or it does not exist.

## What VERIFIED requires

All of it, together:

1. A candidate run that actually ran.
2. A baseline whose outcome is `FAIL` — a repair can only be established against a failure that was
   established first, or a passing candidate proves the behaviour was never broken (INV-02).
3. A candidate outcome of `PASS`. Anything else, `INCONCLUSIVE` included, leaves it unestablished.
4. Closing watermarks from every required producer. A producer that stopped without closing leaves a
   tail nobody can account for, and a contiguous chain does not cover that (INV-06).
5. Protected functional regressions passing: validation, authorization, successful submission, failed
   input handling. A patch that fixes an announcement by removing the thing announced passes the
   accessibility assertion and breaks the application.
6. Frozen assertions and observer contract unchanged between the two runs (INV-03).
7. Identities differing only by the approved patch and differences explicitly recorded as permitted
   (INV-04). Unexplained drift in browser, reader, evaluator, fixture or locale disqualifies the pair.

**Missing evidence is INCONCLUSIVE, not NOT_ESTABLISHED.** A run that produced no verdict has not
shown the repair failed — it has shown nothing. Conflating them would let an infrastructure problem
read as a rejected repair, and the next person would go looking for a better patch instead of a
working runner.

**A failed verification removes nothing.** The finding keeps its status and all its evidence; a test
asserts the finding is still `REPRODUCED` afterwards. The opposite — a failed repair attempt quietly
downgrading the finding it failed to fix — would make trying a patch a way to make a defect go away.

Every attempt is listed, never a selected one. That is the difference between a verification and a
search for a favourable result.

## Verification of this module

24 integration tests against real PostgreSQL 17, including one parameterised case per gate: a single
test asserting "not verified" would pass if only one gate worked.

Mutation checks on the dispatch recheck, the base-digest comparison, the candidate-outcome gate, the
drift check, the lifecycle transition table, the conclusion-is-frozen guard, and two schema
constraints (`verified_requires_a_candidate`, forced RLS). All caught; files restored byte-identically.

## Limitations — read these before quoting anything

- **No candidate has ever been built or run by this product**, and there is no longer any way to
  pretend otherwise. The fabricated-evidence helper is gone; the `VERIFIED` branch is marked
  unreachable and no test exercises it, because no test can without a runner.
- The module prompt's acceptance gate — reproduce the baseline on the reference application's real
  backend, apply the approved patch, rerun under the pinned VoiceOver profile — **has not been run**.
  Per its own stop condition, runtime proof is marked BLOCKED and no repair is marked VERIFIED.
- `POST /patches/{id}/verifications` says so in its response: `runtimeProof` states that no candidate
  can be produced here.
- ~~The gates trust what the caller reports about a candidate run.~~ **Closed.** They read recorded
  rows. What remains is that one input has no recorded source yet: protected functional regressions.
  `_regression_attestation` is the single place a runner will supply them, and until then it returns
  False — so the system is conclusively non-VERIFIED rather than trusting a claim.
- Human review remains a separate dependency. `VERIFIED → REVIEW_ACCEPTED` is in the lifecycle; no
  route drives it yet, and `RESOLVED` on a finding still requires review that module 16 owns.
