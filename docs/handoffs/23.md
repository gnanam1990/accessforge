## What exists now

Two screens replaced their not-built placeholders: a run and a finding. Between them a reviewer can
read what a run's status and outcome actually say, what evidence exists for one attempt, what is
missing from it, and how a finding got to its current status — with the machine's claim and a
person's claim kept separately attributable.

Three routes were added to serve them: `GET /runs/{id}/attempts`, `GET /runs/{id}/timeline` and
`GET /runs/{id}/completeness`.

## The three distinctions this module exists to keep

**Order is the sequencer's, never a clock.** `/timeline` orders by the integer position the trusted
sequencer assigned inside the transaction that admitted each record. Producers submit source times
from their own machines, those disagree, and the response says so in `orderingMeaning`. The
integration test admits an observer record whose source time is an hour *earlier* than the
supervisor record already in the chain; sorted by that field it would come first, and a reviewer
would be shown a sequence that never happened. It appears where it belongs.

**Contiguity is not completeness (INV-06).** `contiguous` and `producersClosed` are separate fields
because they are separate properties. A producer that stops halfway leaves a perfect contiguous
chain covering half the attempt, and a single `complete` flag would be true of exactly that attempt.
The completeness response has **no outcome field at all** — a test asserts the absence — because
completeness is an input to a verdict, not a verdict: a complete evidence set can still describe a
failure, and an incomplete one does not become a pass by being tidy.

**A supervisor receipt is not observer proof.** Every timeline entry carries the producer that
submitted it, its own record number and the source-record digest, as labelled fields rather than as
a colour or an icon.

## What the screens refuse to say

`runStatus.ts` holds the exact copy UI-UX section 5 specifies for each situation, in one place,
derived only from server-owned fields. `PASS` appears in **one branch**, reached only when the
server has already said both `COMPLETED` and `PASS` — and a test walks eight other status/outcome
pairs asserting none of them produces a pass tone, a pass situation, or the word "passed". There is
no path by which a green-looking last event, a completion receipt or a full evidence set becomes a
pass on this screen.

The rest of the vocabulary, each chosen to stop a particular over-reading:

| Situation | What the screen says |
|---|---|
| `QUEUED` | "Waiting for an eligible runner." Nothing has run |
| `RUNNING` | The current admitted step and the budget. No provisional success badge |
| `FINALIZING` | "Validating evidence." Upload progress is not evaluation |
| `COMPLETED` / `PASS` | Passed **on the listed build and profile**, with the untested scope attached |
| `COMPLETED` / `FAIL` | A required assertion was false, established from evidence |
| `COMPLETED` / `INCONCLUSIVE` | "Nothing was established" — not a pass and not a defect |
| `INTERRUPTED` | Terminal; a retry is a new run with fresh fixtures, never a resume |
| Cancellation requested | "Waiting for runner acknowledgement." Checked **before** the status, because the status says `RUNNING` and the thing a person needs is that nothing established the desktop stopped |
| `CANCELLED` with a stop | "Runner stop acknowledged", and it does not undo effects already performed |
| `CANCELLED` with none | "Cancelled before dispatch" |
| Anything else | Reported as unrecognised, with the raw pair, rather than mapped to the nearest familiar one |

**The timeline is a semantic ordered list**, paginated, completely in the DOM. Virtualization is an
optional visual optimisation requiring an equivalent complete accessible mode; this *is* the
complete mode, so there is nothing to be equivalent to yet. Payloads sit behind a per-event
disclosure with `aria-expanded`, search filters and says that it is filtering, and an empty page is
called missing evidence rather than a quiet successful journey.

**Previous is a cursor trail, not arithmetic.** A keyset cursor is not reversible, and computing a
previous position by subtracting a page size would skip or repeat events whenever a page was short.

**The finding screen keeps two claims apart (INV-12).** Machine outcome and human assessments are
separate sections, each carrying the server's own sentence about how it was established, with the
consequence stated: an accepted review cannot make an inconclusive run pass. No status control is
offered — reproduction requires a complete valid failed run, and a transition control on a read-only
inspection page would be a way to acquire a `REPRODUCED` badge by opinion.

## The gap that matters most

**Per-assertion results do not exist and the screen says so.** The evaluator is a pure function in
`packages/domain/.../evaluation`; nothing assembles its inputs from a stored attempt, and no route
serves a per-assertion result. The acceptance gate asks that a reviewer be able to state *which
exact assertion failed*, and they cannot.

What the screen does instead is print a notice saying the results are not available, why, and what
would be needed. Listing the run's outcome once per assertion would have satisfied the gate's
appearance and would have been this interface inventing the thing it exists to report. That is the
one substitution this product cannot make.

## Four more, from the independent review

Three were real and are fixed; one is declined for the reason module 22 recorded.

**An attempt was read without checking it belonged to the run.** Row-level security hides another
tenant's attempt, and that is not enough: an attempt id from a *different run in the same workspace*
is perfectly visible and passes a UUID check. The timeline returned a plausible empty page for the
mismatched pair, and the completeness route returned **that other attempt's producer streams** —
one run's evidence on another run's screen. Both routes now bind the pair and answer 404, and so do
module 18's `/events` and `/evidence`, which had the same hole.

**The source-record digest was dropped.** The API supplies it and the provenance block did not
render it, so a reader could not identify the producer's own record. It is now shown, and the
mutation that substitutes the payload digest — a different value entirely — is killed by a test.

**Timeline pagination survived a change of attempt.** React kept `TimelineSection` mounted across
the switch, so its page cursor and cursor trail carried over: the new attempt's timeline started
partway in and Previous walked back through positions belonging to the old one. It is now keyed by
the attempt.

**Declined: documenting the reachable problem responses in the contract.** The finding is correct —
these operations advertise 200 and 422 while returning 400 and 404. It is the same contract-
completeness work module 22 declined, for the same reason: every route in this repository generates
its schema from `dict[str, Any]`, and documenting three of thirty-two would leave two conventions in
the tree. Recorded rather than half-done.

### Against the real API, in a real browser

A run and an attempt were seeded through the real sequencer with four admitted records, one of them
an observer record whose clock reads an hour behind the supervisor's. Observed on the run screen:

- The timeline rendered `#1 RUN_STARTED`, `#2 ACTION_DISPATCHED`, `#3 READER_OBSERVATION`,
  `#4 ACTION_DISPATCHED` — the observer record at position 3, where the sequencer put it, not first
  where its own clock would have placed it.
- Each entry labelled with its producer: `supervisor-1`, `supervisor-1`, `observer-1`,
  `supervisor-1`.
- Completeness reported **chain contiguous: no gaps** *and* **producers closed: some still open**,
  with both reasons in full, including the INV-06 sentence about a perfect chain and half the
  evidence, and the unbounded-extent reason.
- "What happened" read `QUEUED` / `NOT_EVALUATED` with "Nothing has run", and the separate-fields
  explanation beneath it.
- The assertion-results section read "Not available in this build", with the reason.

### The mutant that survives, and why it stays

The producer-stream query carries `run_id` as well as `attempt_id`. `_bound_attempt` already refuses
a mismatched pair before the query runs, so through the route that predicate can never change the
answer, and no test reaches it. It stays anyway: it makes the query correct on its own terms rather
than correct because of what a caller did first, and this is the exact read that previously
attributed one run's producer streams to another run's screen.

That is a different judgement from the one module 22 made about an unreachable re-entry ref, and the
difference is worth stating. The ref duplicated a guard that already worked and invited a reader to
believe the danger was handled somewhere else. This predicate is not a duplicate control-flow
check; it is the query saying what it means. The comment above it says it is unreachable, so nobody
reads it as load-bearing.

### What the browser could not confirm

The per-event disclosure's keyboard activation was driven by `userEvent` in the unit tests, not in
the live browser: the in-app browser pane reported a zero-size viewport for part of this session, so
dispatched key events did not reach the page. The control is a native `<button>` with
`aria-expanded`, so its Enter and Space behaviour is the platform's rather than this code's — but
that is an argument, not an observation, and it is recorded as one.

## What is not proved

**No run has ever executed.** Every event in the verification above was admitted by a seeding
script through the real sequencer, not produced by a desktop. There is no reader transcript, no
observer receipt from a real application, no artifact, and no interrupted run that was interrupted
by anything. The prompt asks for "real recorded reference-application events and an intentionally
interrupted run"; what exists is a real chain of synthetic records, which proves the ordering,
provenance and completeness logic and proves nothing about a screen reader.

**The acceptance gate is partly met.** A fresh reviewer can state what happened, what evidence is
unavailable, and what the next safe action is. They cannot state which exact assertion failed,
because nothing serves that. A reader startup failure would be visibly `INCONCLUSIVE` — the copy and
its test exist — but no reader has ever started, so that has not been observed.

**Cancellation is untested against a runner.** The screen reports what the server proved, and the
server has never had a runner to prove anything about.

**No SSE, and no live updates.** Task 10 asks for reading position and focus to be preserved during
stream updates and reconnects. There is no stream: module 19 built the durable primitives and no
route serves them over SSE. Nothing on this screen updates by itself, so there is no focus to
preserve — which means the requirement is unmet rather than satisfied, and the reconnect behaviour
remains proved only against the primitives.

**No actual screen reader, and no automated accessibility scan** — the same position as modules 21
and 22, for the same reasons.

**Media, transcripts and redaction are absent.** Tasks 4 and 5 ask for audio and video handling with
transcripts and privacy warnings, and for redacted content to show its reason and evidence impact.
No artifact of that kind exists to render, and no route serves one, so none of it was built rather
than mocked.
