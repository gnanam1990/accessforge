# Module 14 — Constrained patch proposal

**Scope built:** the proposal and authorization half. **Not built:** the sandbox, the candidate build,
and every containment claim that depends on executing code. Read the limitations before relying on
anything here.

## What exists

`POST /findings/{findingId}/patches` records a change somebody proposes — the **exact bytes**, per
path, with the file mode and whether the file is deleted — against a base identity in both halves:
the sealed manifest the baseline ran against, and the source tree that manifest actually sealed.

Both halves are checked. The manifest digest must name a sealed manifest, and `baseSourceDigest`
must be the `tree_digest` of the `source_snapshot` that seal points at. Without the join it was any
64-character hex string the caller chose, which made the stale-base check at dispatch compare the
current tree against a number somebody typed.

The changes live in `patch_change`, one row per path, and `load_patch` recomputes their digest on
every read — unconditionally — and refuses the proposal if it disagrees with the approved one. The
comparison was originally skipped when there were no rows, which meant deleting every change
returned an empty patch still carrying its recorded digest, its APPROVED status and a live approval:
the one shape a caller reads as an authorized change and applies as nothing. A guard that stops
guarding when the thing it guards is missing is not a guard, and zero rows is the case that cannot
arise honestly, because `propose_patch` refuses a patch that changes nothing. A proposal that stored
only filenames was not a patch: nothing could reload what was proposed, a reviewer could not read
what they were approving, and the bytes an approval bound to existed only in the request that
created it. Size limits (256 KiB per change, 2 MiB per patch) keep "reviewable" true rather than
aspirational.

`POST /patches/{patchId}/approval` transitions the patch to APPROVED and **then** mints the
`PATCH_APPLY` approval, bound to the digest and to the revision the patch has once approved.

That ordering is load-bearing. The transition bumps the revision, so an approval minted beforehand
records the pre-transition number — and a dispatch check comparing it against the patch's current
revision would then reject every legitimate approval. The first version hid that by comparing the
approval's `expected_revision` against itself, which is a check that cannot fail: a patch edited
after approval stayed dispatchable. Minting after the transition is what lets the real check run.

`If-Match` is required: an approval is a decision about the bytes the approver read. The approval is
minted server-side rather than accepted as a client-supplied id, so its `target_digest` cannot name
anything other than this patch, and there is no window in which an approval exists for a patch that
was never approved.

`patches.assert_dispatchable` is the recheck at the moment of application. The gap between approving
and applying is where the interesting failures live: revocation, expiry, and the source tree moving
underneath the approval. A moved base raises `StalePatchBase` specifically, because the caller's
correct response differs — a revoked approval means ask again, a moved base means propose again
against what is there now.

## The policy is the product

`accessforge_domain.patch_policy` decides what a repair may touch. It is pure, which is what makes
the boundary testable without the containment this deployment has not got.

The risk it addresses is not a wrong patch — a wrong patch fails verification and costs nothing. It
is a patch that is **right about the wrong thing**:

| Refused | Because |
|---|---|
| tests, specs, `*_test.*`, `__tests__/` | the cheapest way to make a failing assertion pass is to edit the assertion |
| authorization, authentication, permissions, RBAC | "the submission succeeds now" is achievable by deleting the permission check |
| validation and sanitization | the journey is about the error a validator produces; deleting the validator removes the error instead of announcing it |
| consent and privacy | neither is an accessibility defect |
| CI configuration, Dockerfile, Makefile, `.env*`, secrets | a patch that edits the pipeline chooses how it is checked |
| AccessForge's own evaluator and evidence code, anything named `fixture` or `oracle` | a patch that can reach what grades it grades itself (INV-03) |
| `..`, absolute and `~` paths, backslashes, null bytes | outside the candidate workspace by construction (INV-16) |
| symlinks (mode `120000`) | every path in the diff stays inside the tree while the link points wherever the build user can read |
| binary replacement | a reviewer cannot read it, so approving it approves bytes nobody has seen |

Dependency manifests, lockfiles and build config are **not** refused — sometimes the repair really is
a library upgrade. They return as `separatelyReviewed`, proposing them requires
`acknowledgeSeparateReview`, and they appear at the top level of the response, because a reviewer told
"fixed the label" would not otherwise know the lockfile moved.

The repair surface bounds what a patch may touch, and it is **configuration, not request input**:
`PUT /projects/{projectId}/repair-surface`, written with `PROJECT_CONFIGURE`. It used to arrive in
the proposal body as `applicationPaths`, which meant the agent proposing a change also chose how far
it could reach — and an omitted list disabled confinement entirely, so the laziest request got the
widest surface. A project with no configured surface now accepts no proposals: "unconfigured" must
not mean "unrestricted" for the one setting that bounds what an agent may rewrite.

Protection beats the surface: a project declaring `tests/` has not opted out of the rule that makes
a verified repair mean anything. The prefix match is segment-aware, so `web` does not authorize
`website`.

The base identity is bound to the finding's **own run**, not to anything the workspace sealed. Before
that, a patch for a finding about run A could be recorded against run B's manifest, and every later
check agreed with itself: the approval bound to B's digest, the stale-base check compared B's tree,
and the verification compared a candidate against a baseline it was never about.

## Verification of this module

- 41 unit tests over the policy, one per forbidden category, each a change that would verify cleanly
  while making the product worse.
- 50 integration tests over proposal, approval, dispatch and verification against real PostgreSQL 17.
- 22 mutation checks across the policy, the persistence gates and the schema — the protected list,
  the allowlist, symlink mode, traversal, the dispatch revision comparison (reinstating the original
  self-referential bug), minting before the transition, the sealed-tree check, the digest-on-reload
  check, mode loss on reload, and four schema constraints. Each breaks one guard and names the test
  that fails; each file restored byte-identically by SHA-256.

## Limitations — read these

- **No sandbox, no candidate build, no containment evidence.** Tasks 5 through 9 of the module prompt
  are not implemented. Nothing here executes a build script, so nothing here demonstrates credential
  isolation, metadata denial, resource limits or scratch cleanup. The prompt's stop condition applies:
  hosted untrusted-source support is **blocked**, and no containment claim is made from an
  architecture argument.
- **The policy inspects what it is given.** It rules on paths, content and modes a caller supplies. It
  does not read a repository, so it cannot catch a caller that describes one change and applies
  another. That check belongs to the applying side, which does not exist yet.
- **The stored diff is content, not a patch format.** Each row is the post-change content of a path,
  not a unified diff with context lines, so nothing here verifies the change applies cleanly to the
  base tree. That verification belongs to the applying side too.
- **`PATCH_APPLY` authorizes nothing outside a candidate workspace**, and no scope in this product
  authorizes a merge or a deployment — `authorizes_merge_or_deploy` returns False unconditionally.
- **No real model has proposed a patch.** Module 13's diagnosis is wired to a bounded projection, not
  to Bedrock; proposals in every test here are written by the test.
