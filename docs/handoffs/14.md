# Module 14 — Constrained patch proposal

**Scope built:** the proposal and authorization half. **Not built:** the sandbox, the candidate build,
and every containment claim that depends on executing code. Read the limitations before relying on
anything here.

## What exists

`POST /findings/{findingId}/patches` records a change somebody proposes, against a base identity in
both halves: the sealed manifest the baseline ran against, and the exact source digest. A proposal
against a manifest this workspace never sealed is refused — otherwise an approval would bind to
inputs nothing recorded.

`POST /patches/{patchId}/approval` mints a `PATCH_APPLY` approval bound to this patch's digest and
revision, and attaches it. `If-Match` is required: an approval is a decision about the bytes the
approver read, and a patch amended in between would carry an approval for something nobody saw. The
approval is minted server-side rather than accepted as a client-supplied id, so its `target_digest`
cannot name anything other than this patch.

`patches.assert_dispatchable` is the recheck at the moment of application. The gap between approving
and applying is where the interesting failures live: revocation, expiry, and the source tree moving
underneath the approval. A moved base raises `StalePatchBase` specifically, because the caller's
correct response differs — a revoked approval means ask again, a moved base means propose again
against what is there now.

## The policy is the product

`accessforge_domain.patch_policy` decides what a repair may touch. It is pure, which is what makes
the boundary testable without the containment this deployment has not got.

The risk it addresses is not a wrong patch — a wrong patch fails verification and costs nothing. It
is a patch that is **right about the wrong thing**:

| Refused | Because |
|---|---|
| tests, specs, `*_test.*`, `__tests__/` | the cheapest way to make a failing assertion pass is to edit the assertion |
| authorization, authentication, permissions, RBAC | "the submission succeeds now" is achievable by deleting the permission check |
| validation and sanitization | the journey is about the error a validator produces; deleting the validator removes the error instead of announcing it |
| consent and privacy | neither is an accessibility defect |
| CI configuration, Dockerfile, Makefile, `.env*`, secrets | a patch that edits the pipeline chooses how it is checked |
| AccessForge's own evaluator and evidence code, anything named `fixture` or `oracle` | a patch that can reach what grades it grades itself (INV-03) |
| `..`, absolute and `~` paths, backslashes, null bytes | outside the candidate workspace by construction (INV-16) |
| symlinks (mode `120000`) | every path in the diff stays inside the tree while the link points wherever the build user can read |
| binary replacement | a reviewer cannot read it, so approving it approves bytes nobody has seen |

Dependency manifests, lockfiles and build config are **not** refused — sometimes the repair really is
a library upgrade. They return as `separatelyReviewed`, proposing them requires
`acknowledgeSeparateReview`, and they appear at the top level of the response, because a reviewer told
"fixed the label" would not otherwise know the lockfile moved.

`applicationPaths` bounds the repair surface. Protection beats the allowlist: a project declaring
`tests/` as its surface has not opted out of the rule that makes a verified repair mean anything. The
prefix match is segment-aware, so `web` does not authorize `website`.

## Verification of this module

- 41 unit tests over the policy, one per forbidden category, each a change that would verify cleanly
  while making the product worse.
- 18 integration tests over proposal and approval against real PostgreSQL 17.
- 10 mutation checks across the policy and the persistence gates — the protected list, the allowlist,
  symlink mode, traversal, the dispatch recheck, the base-digest comparison. Each breaks one guard
  and names the test that fails; each file restored byte-identically by SHA-256.

## Limitations — read these

- **No sandbox, no candidate build, no containment evidence.** Tasks 5 through 9 of the module prompt
  are not implemented. Nothing here executes a build script, so nothing here demonstrates credential
  isolation, metadata denial, resource limits or scratch cleanup. The prompt's stop condition applies:
  hosted untrusted-source support is **blocked**, and no containment claim is made from an
  architecture argument.
- **The policy inspects what it is given.** It rules on paths, content and modes a caller supplies. It
  does not read a repository, so it cannot catch a caller that describes one change and applies
  another. That check belongs to the applying side, which does not exist yet.
- **`PATCH_APPLY` authorizes nothing outside a candidate workspace**, and no scope in this product
  authorizes a merge or a deployment — `authorizes_merge_or_deploy` returns False unconditionally.
- **No real model has proposed a patch.** Module 13's diagnosis is wired to a bounded projection, not
  to Bedrock; proposals in every test here are written by the test.
