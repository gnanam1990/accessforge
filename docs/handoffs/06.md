## The E0 journey and its generated digests

One scenario: form-error recovery. Submit an invalid email, encounter the announced validation error,
correct the named field, create exactly one request.

Compilation produces four digests, deterministically — the same reviewed draft yields the same values
every time, which is what lets a baseline and a candidate be shown to share their journey exactly:

```
journeyDigest            over name, platform, intent, the three digests below, effects and budget
assertionSetDigest       over the ordered assertions, each with its observer and unknown reasons
fixtureDigest            over template, navigator values, and digests of reset/observer material
navigatorPolicyDigest    over exactly what the navigator may see and do
```

**What is deliberately absent from the journey: an expected action sequence.** A journey specifying
keystrokes would be a replay of a known-good path, and passing it would say nothing about whether a
real reader user could accomplish the task.

## Protected assertions

| Kind | Decided by | Why only that observer |
|---|---|---|
| TASK_COMPLETION | APPLICATION_OBSERVER | A phrase announced on screen is not evidence a row was written |
| REQUIRED_ANNOUNCEMENT | READER | A backend row proves nothing about what was spoken |
| FOCUS_BEHAVIOUR | READER | Only the reader sees focus |
| READING_ORDER | READER | Likewise |
| FORBIDDEN_EFFECT | EFFECT_MONITOR | Its true value is absence |
| FUNCTIONAL_VALIDATION | FUNCTIONAL_TEST | Makes INV-16 checkable: a repair that loosened validation fails here |

Each kind maps to exactly one observer. A kind decidable by two would let the weaker answer for the
stronger.

**Every required assertion must declare how it can be unknown.** A condition that can only be true or
false cannot represent a missing observation, which is precisely how an unobserved assertion becomes a
reported defect. Authoring refuses it (INV-02 at authoring time).

A journey must include a required TASK_COMPLETION assertion; marking it optional does not satisfy the
rule. Required completion is a frozen condition, not an optional extra.

## Protected interfaces for modules 07, 12 and 11

- **Runner control (07):** `compile_journey(...).version` carries the four digests for sealing;
  `navigator_policy` is the sealed statement of permitted actions, chords and budgets.
- **Navigator (12):** `navigator_policy` and `fixtures.navigator_values` are the *only* inputs. The
  policy names its own prohibitions, and `navigator_values` has no parameter through which oracle
  material could be requested — a single reader with an `include_oracle` flag would be one careless
  call from handing over the answer key.
- **Outcome verification (11):** `AssertionSet.required` plus each assertion's `observer` and
  `unknown_reasons` feed the precedence rules directly.

## A silent collision worth recording

The product's fixture table was first written as `fixture_instance` — the same name the reference
application under test already uses, in the same local database. `CREATE TABLE IF NOT EXISTS` did
nothing, silently, and the product would have been reading the application's rows. Renamed to
`run_fixture_instance`.

The test written alongside that rename asserted only that both tables were present. That made it
depend on ambient state: it passed on a development database that happened to hold the application's
schema and proved nothing on a fresh one, where the application's table does not exist at all. It now
applies the application's real schema itself, then asserts where a write actually lands — the
product's row in the tenant-scoped table, the application's table still empty.

The limitation is worth stating plainly: the original defect was a *silent* collision, and it can no
longer be reproduced, because the two tables now have incompatible schemas and a misdirected write
fails loudly rather than quietly. The test proves the product uses its own table; it does not
reconstruct the silence.

## What a carried-over development database hid

Both defects above reached CI because the local database was not fresh. Module 06 was branched from
module 04's head and shipped migration `0007`, which references the `project` table that `0005`
creates. The local database still held `0005`'s tables *and* still recorded `0005` in
`schema_migration`, so `migrate` skipped nothing it needed and every `CREATE TABLE IF NOT EXISTS`
succeeded. CI, on a fresh database, failed with `relation "project" does not exist` raised from the
setup of an unrelated authentication test — thirty-odd errors, none of them naming the cause.

Two preconditions now run before `migrate` sends a statement, both in `_migration_paths` and
`migrate`:

- The series on disk must be consecutively numbered from `0001`. A branch carrying `0007` without
  `0005` and `0006` is refused by name, with the advice to rebase. This catches the fault on a fresh
  database, which is the case CI exercises.
- The database must not record a migration absent from this tree. That condition means the schema was
  built by a different branch, and nothing applied on top of it can be trusted. This catches the
  fault on a carried-over database, which is the case that hid it.

Duplicate numbers (two branches both numbering `0003`) and unnumbered files are refused for the same
reason: their relative order would depend on the rest of the filename.

`packages/persistence/src` was also absent from CI's strict `mypy` targets — the one package holding
every tenancy decision. It already passed; it is now checked.

The verification procedure has gained the step that would have caught all of this: `dropdb` and
`createdb` before the integration suite, not a database carried between branches.

## Findings from the independent review

The automated reviewer on this pull request raised eight issues. Seven were real and are fixed, each
with a regression test and a mutation showing that test fails without the fix. They are listed here
because the pattern is worth seeing: every one of them is a boundary that *looked* enforced.

| Finding | Why it was real |
|---|---|
| `ASSERTION_OBSERVERS` was a plain module-level dict | `Assertion.observer` reads it at access time rather than storing the value, so reassigning an entry changes which identity is authoritative for an assertion **without changing that assertion's digest**. A sealed journey would keep its digest and start accepting the navigator's own word for what the reader announced (INV-05). Now a `MappingProxyType`. |
| `FixtureBinding`'s mappings were mutable | `frozen=True` freezes the field, not the dictionary it points at. The caller kept its reference and could insert the credential or selector the constructor had just rejected, after validation and after the digest — or edit the oracle. Defensive `MappingProxyType(dict(...))` copies are now taken before validation runs. |
| The selector rule required whitespace before the sigil | `(#email)`, `target:#email`, `"#email"` and `at:.email-error` all passed. Punctuation in front of a selector is how one would most naturally be written. The rule is now "not preceded by a word character", which covers all of those and still lets `example.test` and `e.g.` through. |
| Migrations were sorted lexically with an unpadded prefix accepted | `1_a.sql`, `2_b.sql`, `10_c.sql` is a consecutive series that sorts 1, 10, 2 — a dependent migration applied before its prerequisite, which is exactly the failure the new guard was written to prevent, passing every check that guard had. Four-digit width is now required and the series is returned in numeric order. |
| The gap check started at 1, so `0000_bootstrap.sql` was invisible to it | A migration outside the declared series still executes SQL and is still recorded in the ledger. Numbers below 1 are now refused. |
| `journey_version.supersedes` referenced `journey_version (id)` alone | Foreign keys are checked by the system, which every row-level security policy exempts, so the constraint would have accepted **another tenant's** journey version as a predecessor — lineage pointing at a row the citing workspace can never read or audit (CWE-639). Now composite on `(supersedes, workspace_id)`, matching every other cross-row reference in this schema. |
| The reviewer summary omitted `Assertion.description` | It listed the identifier, kind, observer and unknown reasons — everything except the sentence saying what must be true. Approving from that is approving assertion *names*. |

Two of these were in code written earlier in this same pull request to fix an earlier defect, which is
the ordinary way this goes.

### The one finding not acted on

The reviewer also proposed replacing `digest` with a keyed commitment for `fixture_digest`, on the
grounds that an unkeyed SHA-256 over low-entropy fixture and observer values can be brute-forced
offline by anyone holding an export.

The observation is correct and the remedy is refused, deliberately. CONTRACTS requires exports to be
independently verifiable offline: "Offline verification checks these structures." A commitment keyed
with something an export reader does not hold is a commitment that reader cannot check, which trades
a small confidentiality gain for the loss of the property the digest exists to provide.

The residual exposure is also narrower than it appears. Fixture values are synthetic by construction
— this module refuses credential shapes in them — and the oracle material is expectation counts and
similar, not secrets. What an export reader could learn by guessing is what the run was checked
against, which the reviewer summary in the same export tells them anyway. The boundary this module
enforces is that the **navigator** never sees the oracle during a run, and that is unaffected by what
a later export reader can compute.

Recorded rather than silently declined, and listed as an outstanding item in
`docs/delivery/STATUS.md` so a future decision to make exports confidential has the argument to hand.
