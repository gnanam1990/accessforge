## The crash matrix

Each row commits or rolls back at a specific instant and then inspects what a recovering worker finds.

| Crash point | Observed |
|---|---|
| Before commit | no run, no audit row, no outbox message — nothing half-happened |
| After commit, before publish | message survives and a later publisher claims it; the reference names the run and revision |
| After publish, before acknowledgement | redelivered once the claim lease lapses, with the **same** `operation_id` and `attempts` incremented to 2 |
| After action intent, no result | surfaced by `recovery.ambiguous_attempts`; the only admissible resolution is INTERRUPTED + quarantine |
| SIGKILL mid-transaction, real child process | uncommitted write discarded |

The SIGKILL case uses a genuinely separate process rather than an in-process rollback, because a
rollback models a crash faithfully for the database but not for the question of whether the operating
system kept its promise.

## Concurrency, with real connections

| Case | Observed |
|---|---|
| Two workers claiming one message | disjoint claims via `FOR UPDATE SKIP LOCKED`; the loser finds nothing rather than blocking |

| Two concurrent identical idempotency reservations | one operation; exactly one caller believes it created it |
| Two sequencers on one attempt | serialized; an advisory lock on the attempt key is observed in `pg_locks` |

### Two guards that were present but unprovable

Mutation testing found my **tests** wrong rather than the code, twice, and both are worth recording
because the failure mode is subtle.

**The optimistic revision check was unreachable.** `apply_transition` re-read state under a row lock
and then wrote back the revision it had just read, so the comparison could never fail — removing the
predicate failed no test at all. A guard that cannot fail is indistinguishable from an absent one.
Fixed in the design, not the test: the signature now takes the revision the *caller* last observed,
which is the real concurrency question, and a stale caller is refused. The statement-level predicate
is kept as belt and braces and its presence is asserted separately, with the unreachability recorded
rather than hidden.

**The advisory lock was indistinguishable from the unique index.** A race test expecting a lock
timeout passed with the lock removed, because the second connection blocked on the `canonical_event`
primary key instead. The test now observes the lock directly in `pg_locks`. The constraint would still
catch a collision, but as a crash rather than as serialization.

## Independent review findings and closure

A separate reviewing agent reviewed `141e3de..3ceaef6`. Its environment had no shell, so all four
findings were static analysis; the two substantive ones were reproduced by execution here, and both
were real. The second turned out **more severe** than the reviewer rated it.

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | Replay reported the wrong canonical event when two source records shared a payload | **Critical** | FIXED WITH PROOF |
| 2 | A session could sequence onto another workspace's attempt | **Critical** (rated Important) | FIXED WITH PROOF |
| 3 | A vacuous assertion: `X not in os.environ or True` | test quality | REMOVED |
| 4 | A test asserting on function source text rather than behaviour | test quality | REMOVED |

**Finding 1.** The replay path searched `canonical_event` by `payload_digest` and took the first
match. Two identical reader observations — a reader saying "Loading" twice — are two distinct source
records with the same content, so redelivering the second reported the first one's position:

```
record A -> canonical 1    record B -> canonical 2
replay of B reports canonical 1   <- A's position and A's event id
```

Content is how a replay is distinguished from a conflict; it is not an identity. The canonical
position is now recorded on the source record itself, so a replay answers from provenance. No test
covered two records with identical payloads, which is why mutation testing had not caught it either.

**Finding 2, and it is worse than reported.** `admit_record` trusted the caller's `workspace_id` and
never checked it against the workspace owning the run. Referential-integrity checks bypass row-level
security, so a session scoped to A could insert a row labelled A while chained onto B's
(run, attempt) sequence space.

The reviewer described this as pollution. Reproduction showed a **cross-tenant denial of service**:
B could not see the injected row — its policy filters on workspace — but the row occupied canonical
position 1, so B's own first record failed with a bare `UniqueViolation` on a chain that looked empty
from inside B. Unexplainable from the victim's side.

Fixed in two places. `admit_record` and `close_producer_stream` verify ownership under the caller's
row-level security, so a foreign attempt is invisible and the mismatch is reported. And migration
`0004` replaces the id-only foreign keys with **composite** `(id, workspace_id)` references, so the
database refuses the mismatch whatever the application believes — covering a future caller, migration
or report that never goes through these functions.

**Findings 3 and 4** were my own test defects. `assert X not in os.environ or True` can never fail.
And a test asserting `"WHERE id = %s AND revision = %s" in inspect.getsource(...)` proves a string
exists, not that the executed statement uses it — it would pass with the predicate moved into a
comment and break on a harmless reformat. Both removed; the unreachability of the statement-level
predicate is recorded in ADR 0005 instead, which is more honest than a test that cannot distinguish
presence from correctness.

Mutation checks confirm the fixes bite: restoring the digest-keyed replay fails 1 test; removing the
ownership check fails 1.

## Database-level invariants

Enforced in the schema as well as in the reducers, because the reducers do not see every path:

- admissible status/outcome pairs — CHECK constraint
- an interrupted run must record why — CHECK constraint
- cancellation request and its revision are set together — CHECK constraint
- terminal runs are immutable — BEFORE UPDATE OR DELETE trigger, tested for both
- one attempt per (run, lease epoch) — UNIQUE, which is INV-10 in schema form
- one exact child authorization per run — UNIQUE
- a child must record its issuing service identity — CHECK on a non-blank value
- all eleven new tables carry FORCE row-level security
- evidence tables reference `(run_id, workspace_id)` and `(attempt_id, workspace_id)` compositely, so
  a row cannot name a run or attempt in another workspace
