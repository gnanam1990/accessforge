## Manual controller continuation

`apps/orchestrator/src/accessforge_orchestrator/manual_dispatch.py` connects exact manual consent
to one committed initial handoff. It owns the workspace transaction, locks runner then run,
serializes with approval revocation, and rechecks approval, current permission/environment,
preflight, live lease, expected run revision and the lease's exact attempt/epoch. The reducer
advances LEASED to RUNNING with an audit containing the exact dispatch reference and a transactional
outbox message. Only after commit may the trusted transport receive that reference once.

RUNNING here conservatively records admission: execution may have begun. It is not a reader
observation. Acknowledgement only means reference delivery, not action success or completion.
Repeated or concurrent controller calls cannot send again, including after abrupt process death.
Exceptions, timeout and caller cancellation after commitment trigger exact-attempt recovery:
INTERRUPTED/INCONCLUSIVE, quarantine, and lease release **without** a stop acknowledgement. A late
transport success cannot clear quarantine. Explicit `interrupt(reference)` handles a crashed
controller; no automatic process-owner recovery daemon is implemented by this slice. If the
database is unavailable during recovery, the committed run remains non-replayable and unresolved.

The default transport is unavailable and refuses **before** changing run state. Injected transports
are trusted infrastructure ports, not navigator callbacks or public API input. No production
transport, paid model invocation, reader command or permission grant was enabled. The machine-only
acceptance endpoint below now authenticates receipt. The desktop still needs deployed-byte
re-observation, fresh
per-action authority/effects/budgets and durable local journaling. An asynchronous receiver may
ignore cancellation; quarantine does not pretend to kill it. A blocking transport needs its own
bounded process/network boundary. Physical STOP, observer closure and finalization remain pending.

Regression coverage uses real PostgreSQL/API setup and explicitly synthetic transports: concurrent
controllers, rollback before commit, a real child process exiting abruptly after commit, stale
revision/attempt/epoch/tenant, revoked consent, timeout/cancellation, late success and exact recovery.
None of these are actual-AT release evidence.

## Supervisor ticket reception

Migration0035 adds `supervisor_dispatch_ticket`, one per exact committed run/attempt/runner/lease/
epoch. The controller issues it inside the dispatch transaction, after the RUNNING transition and
exact identity audit. It retains only SHA256 of a fresh256-bit random secret; the secret is sent
only to the trusted transport and omitted from the ticket's repr, audit, outbox and API response.
There is no public ticket-issuance endpoint. Default transport unavailability still prevents both
run mutation and ticket issuance. Expiry is the minimum of30 seconds, lease, approval and manifest
deadlines; the controller bounds its acknowledgement wait by that expiry.

`POST /v1/workspaces/{workspaceId}/supervisor-dispatches/{ticketId}/accept` takes `{}` and exactly one
Bearer header. Human cookies/session tokens, body-supplied identity claims, unknown/expired/revoked
credentials and duplicate headers cannot authenticate a supervisor. Acceptance serializes on the
runner/run/ticket and rechecks current consent, actor role, environment, profile, preflight,
lease/deadline/epoch and the exact durable manual attempt claim. The original initial-dispatch
gate still requires LEASED; the separate receiver gate requires RUNNING. Neither admits an OS action.

Consumption and attributed acceptance audit commit together. The response is `no-store` and says
`DISPATCH_REFERENCE_ACCEPTED`, not started-reader, action success, completion or PASS. Replays,
including the same Idempotency-Key after response loss, are refused. Controller uncertainty revokes
the ticket and interrupts/quarantines; accepted-but-lost-response and late-success tests retain that
distinction. Ticket identity, consumption and revocation cannot be reset, and retained tickets
cannot be deleted/reissued. Workspace erasure remains possible. Backup reconciliation irreversibly
revokes restored tickets, including snapshots taken before the original consumption.

The initial state-change outbox uses the existing `run.running` topic, which the live UI already
subscribes to; the separate `MANUAL_DISPATCH_CLAIMED` audit remains the authority checkpoint. Tests
cover the real published topic and an active UI subscriber re-reading the latest record when a
delayed start notification arrives, without inferring a verdict.
Fake stream delivery now flushes React with `act`, retaining the existing close/restart assertions.

Still pending: an authenticated physical desktop action transport, per-action machine authority
and local journal, actual reader/deployed-byte observations, independent observer ingestion and
closing watermarks, STOP/finalization and matched repair proof. Candidate POST remains closed.

### Native bootstrap receiver

`node apps/desktop-runner/dist/receive-dispatch.js /absolute/private/receiver.json` now implements
the bootstrap-only receiving endpoint. It does not import or start a reader, advertise capability,
execute actions, or replace the default unavailable controller transport. A zero exit means only
`DISPATCH_REFERENCE_ACCEPTED`; it is not permission to call the OS or evidence of PASS.

The operator-provisioned JSON config contains `apiOrigin`, `claimsDirectory` and `localReference`.
The reference has exactly `workspaceId`, `runId`, `attemptId`, `runnerId`, `leaseId`, `epoch`.
The optional `timeoutMs` is in (0,10000], default5000. HTTPS is required; explicit
`allowLoopbackHttp: true` permits only numeric loopback HTTP for local deployment/testing. Origins
with userinfo, query, fragment or a non-root path are refused. Dispatch input cannot choose an API
origin or supply a reader command. TLS verification uses Node defaults; do not disable it.

The trusted controller passes one JSON envelope via stdin, never argv or environment: `reference`
and `ticket`, with the latter containing exactly `ticketId`, `token`, `expiresAt`. The private config
contains no token. Config is limited to8192 bytes; stdin and HTTP response each to4096. The CLI has
a10-second hard ceiling; HTTP waits also obey the earlier ticket/deadline, counting durable-storage
latency. Redirects are not followed, and errors never echo credentials, payloads or server replies.

Before any request, the receiver checks the exact configured local identity and exclusively creates
`claimsDirectory/<normalized-run-id>.json`, writes a token-free RECEPTION_INTENT and fsyncs the file
and directory. Concurrent/restarted receivers, UUID case aliases and alternate tickets for that run
cannot send again. No code deletes a claim, including partial claims and failures before or after
acceptance. A crash or lost/malformed/late/wrong-identity response leaves reception UNKNOWN: retain
the claim and reconcile through the existing controller recovery; never retry or infer physical STOP.
The server receipt now includes all six immutable reference fields and ticket identity, all checked
before acknowledgement. Older servers' incomplete receipt shapes fail closed.

Config and claims must be absolute, canonical nonsymlink paths owned privately by the process user
(for example0600 config,0700 claims directory). This requires POSIX ownership/mode checks; Windows
is refused until a real ACL/handle implementation exists. The operator must retain an exclusive,
stable storage tree and protect its parents. This is not isolation from malicious same-user/root
processes, filesystem rollback, or operator deletion/replacement. Never clear claims to retry a run.
The claim is bootstrap metadata, not an action journal or execution-approval record.

Node tests exercise real sockets, concurrent calls, every identity mismatch, unsafe storage, bounds,
redirects, lost replies, timeout, child-process SIGKILL/restart and secret-safe stdin/output. Python
integration launches the compiled Node CLI against real FastAPI HTTP and PostgreSQL, proving single
DB consumption and fresh revoked-approval refusal, with zero actions/canonical events. Its preflight
and initial controller transport are deliberately synthetic; these are not actual-reader tests.

### Automatic abandoned-handoff recovery

`accessforge_orchestrator.maintenance.handoff_worker` periodically scans explicitly configured
workspaces under RLS. It reuses exact manual interruption/quarantine when an unconsumed ticket
expires, a ticket is revoked, or a lease expires/is released without valid STOP. Accepted-ticket
expiry alone leaves a live execution lease alone. Runner/run/lease locks and a fresh eligibility
query protect against stale snapshots and heartbeat extension; each attempt commits independently.
Concurrent owners are skipped, database contention deferred, and newer epochs are never quarantined
by stale handoffs. The worker sends nothing, grants nothing, resets nothing and records no action.

The executable supports repeated `--workspace-id`, a bounded interval and `--once`; deployment
instructions are in the operations runbook. Targeted real-PostgreSQL smoke coverage exercises seven
recovery/leave-alone cases, including the real child-process CLI and cross-workspace invisibility.
This closes automatic abandoned-manual-handoff recovery, not general action/build/observer recovery
or actual physical execution. No broad suite rerun was required for this isolated worker change.

### Native machine session and action-intent continuation

Migration0036 adds a one-per-ticket execution session. The receiver generates a new256-bit secret
in memory and POSTs it to `/supervisor-dispatches/{ticketId}/session` using the original bootstrap
Bearer. Consumption and session creation commit together; the response contains identity/expiry
only. `/accept` remains bootstrap-only and cannot subsequently be upgraded. No historical session
is minted during migration, and neither the secret digest, identity nor expiry can be rewritten.
An expired/lost acknowledgement is not a retry path. Parent-ticket revocation, including restore
reconciliation, invalidates continuing authentication as well.

`NativeExecutionSession.open(privateConfig, envelope)` implements this path using the same fsynced
exclusive run claim, fixed-origin/no-redirect/bounded HTTP protocol. Its independent secret uses JS
private fields and is not exposed by JSON serialization. `retainIntent(command)` sends to
`/supervisor-sessions/{sessionId}/action-intents` with that secret, never the consumed bootstrap token.
Commands carry `action`, contiguous `sequence`, observed `origin`, and only the applicable
`keyChord` or `textValueRef`; arbitrary text, selectors and run/lease identity claims are not fields.

The server derives identity from the ticket, rechecks live manual consent/lease/preflight/epoch,
compares the sealed navigator-policy digest/action/chord allowlists, resolves typing through the
run fixture, enforces environment origin and both journey/canonical budgets, and retains exactly
one unresolved intent. A second/replayed/ambiguous intent is refused. The native client retains its
pending fence before sending and does not offer blind restart/resume or an unproven reset.

`ACTION_INTENT_RETAINED` is NOT a physical dispatch permit, action success or canonical observation.
The authenticated bridge below adds local journaling and dispatch/result sequencing. Concrete
production origin/focus/deployed-byte/effect/watchdog probes, reader startup, observer closure and
STOP/finalization still need integration. Default production reader transport and candidate POST
remain closed.

Focused checks: eight session/intent HTTP cases and one compiled-Node/real-FastAPI/PostgreSQL case
pass. They prove credential separation, live revocation, replay fencing, exact native receipt,
non-dispatched intent storage and immutable session fields—not actual-reader execution. Native
bootstrap regressions remain passing; no repeated full-suite run was performed.

### Authenticated action execution/result bridge

The machine session now exposes exact-action `/actions/{actionId}/dispatch` and `/result`
endpoints. Dispatch rechecks current session/consent/epoch/lease, the retained origin, sealed policy
and time budget before committing delivery once. A dispatch commitment does not prove OS input.
Known results require a dispatched unresolved action. Ambiguity can close an unresolved intent and
atomically interrupts/quarantines the run and revokes the handoff. Results never mint canonical
observations or a run verdict, and cannot resurrect expired or revoked authority.

`AuthenticatedRunner` joins this session to the existing local Supervisor and VoiceOver adapter
interface. It requires trusted live preflight, actual-origin and physical focus/effect authorization
ports; no default true report or adapter is supplied. Server identity is retained alongside local
journal identity and supplied to observation recording. The local intent is durably flushed before
physical input, and the local result before the server result report. FileJournal completes partial
writes, creates new files with0600 permissions, and fsyncs both file and parent directory.

Only an exact result acknowledgement admits another intent. Lost acknowledgements, journal failures,
timeouts and ambiguity fence the runner without replay/reset. Cancellation and late completion of
physical probes cannot initiate input after the active dispatch has ended. Already-started physical
work remains ambiguous on timeout; this bridge does not claim it can undo OS input.

Focused validation:9 real API/PostgreSQL cases, including3 compiled-Node/real-HTTP cases with real
FileJournal and synthetic physical adapters, passed. The native bridge/supervisor/receiver suites,
desktop build/typecheck, changed Python static checks and83-operation client drift checks passed.
The previous head's CI failure was10 stale forward-migration expected lists missing0035; these
explicit lists were corrected without weakening assertions, and the32-case migration module passed.
No repeated full-suite run or test/CI disabling. Actual VoiceOver execution and production readiness
remain unproven; the private per-attempt journal path and concrete physical guards are host-owned.

## The interfaces modules 08 and 09 must implement

Module 07 deliberately stops at one seam. A screen-reader adapter supplies exactly this:

```ts
dispatch: (command: ActionCommand) => Promise<'SUCCEEDED' | 'FAILED'>
```

Four properties of that contract are load-bearing for the adapters:

1. **It may reject or never settle.** Both are treated identically — `AMBIGUOUS`, desktop fenced. An
   adapter must not convert "I lost the channel" into `FAILED`, because a rejected promise is not
   evidence the operating system did nothing.
2. **It is called at most once per `actionId`.** There is no retry anywhere in the protocol. An
   adapter that retries internally is breaking INV-09 on the supervisor's behalf.
3. **It is called only after the intent is on disk.** The adapter can rely on that: if it is running,
   a durable record of the request already exists.
4. **It does not decide readiness.** The adapter supplies observations for
   `PreflightCheck.READER_ACTIVE`, `SPEECH_CAPTURE_WORKING`, `NO_STALE_INPUT_SOURCE` and the
   permission checks; the server concludes READY. There is no field an adapter can set to say it is
   ready.

The fourteen `PreflightCheck` values are the closed vocabulary an adapter reports into. Adding one is
a deliberate edit to `REQUIRED_PREFLIGHT_CHECKS`, in one place, visible in a diff — because adding a
check to the enum without adding it there would create an optional proof of desktop safety.

## The lease lifecycle

```
                      enroll (single-use token)
                               |
                               v
OFFLINE  <------------>  PREFLIGHT_REQUIRED  <-------------------+
   |                           |                                 |
   |                    successful preflight                     |
   |                           v                                 |
   |                        READY ---- admit_lease ----> BUSY     |
   |                           |        (epoch N+1)       |       |
   |                           |                          |      stop acknowledged
   |                           |                          |      for epoch N+1,
   |                           |                          |      no unresolved action
   |                           |                          +-------+
   |                           |
   +------------> QUARANTINED <+---- expiry without stop proof
                     |               ambiguous action
                     |               failed preflight / profile drift
                     |               failed reset / operator request
                     |
              successful reset (fences epoch N)
                     |
                     v
            PREFLIGHT_REQUIRED
```

Two edges do not exist, and their absence is the design:

- **QUARANTINED → READY.** A fenced desktop re-proves itself or stays fenced. Reset proves the old
  session is dead; preflight proves the new one works; they are separate facts.
- **BUSY → READY.** The browser is wherever the finished run left it, so readiness is re-established
  rather than assumed.

## Crash, cancel and expiry results

| Situation | Lease | Runner | Run | Why |
|---|---|---|---|---|
| Cancellation requested | active, `cancel_requested_at` set | BUSY | **RUNNING** | Nothing has established that the desktop stopped. Only new work is fenced. |
| Stop acknowledged, current epoch, nothing unresolved | released `STOP_ACKNOWLEDGED` | PREFLIGHT_REQUIRED | CANCELLED / INCONCLUSIVE | Proof. Outcome is INCONCLUSIVE because execution had begun. |
| Cancellation on a never-leased run | none ever existed | — | CANCELLED / NOT_EVALUATED | Provably never admitted to a desktop, so provably unable to have typed. |
| Stop acknowledged from a superseded epoch | unchanged | unchanged | unchanged | An earlier session's acknowledgement says nothing about the current one. |
| Acknowledgement while an action is unresolved | unchanged | unchanged | unchanged | The supervisor stopped *asking*. The keystroke may still have landed. |
| Lease deadline passes | released `EXPIRED_WITHOUT_STOP_PROOF` | **QUARANTINED** | unchanged | A silent supervisor is not a stopped supervisor. |
| Action result never arrives | released `AMBIGUOUS_ACTION` | **QUARANTINED** | INTERRUPTED / INCONCLUSIVE, `ambiguityReason` | Unknown, and not re-dispatched (INV-09). |
| Supervisor crashes after intent | — | quarantine required | INTERRUPTED | The journal says an action was intended and its result is unknown. |

## The reset contract

`reset_runner` is the only door out of quarantine. It takes `succeeded` from the trusted reset
procedure — never from the runner — and records a proof document plus this warning, verbatim, with
every reset:

> A reset acts on one physical interactive desktop session. It closes the browser profile and
> restarts the supervisor and the screen reader within that session only. It does not kill processes
> outside the runner's own session, and it must not be performed on a desktop someone is using:
> anyone signed in to it will lose unsaved work in the affected applications.

`inspect_runner` returns the active lease, the unresolved actions, the ambiguous actions and that same
warning, because "is anything still in flight" is what decides whether a reset is an inconvenience or
an interruption of something in progress.

## A gap between modules 04 and 07

`lease_epoch` was on `RunState` and on the `run` row from module 04, was written by every transition,
and was never *set* by anything — no reducer took an epoch. A run's epoch stayed `0` for its whole
life, so `acknowledge_stop`, which refuses an acknowledgement whose epoch does not match the current
one, would have refused **every acknowledgement that could ever exist**. A stop could never be proved;
no run holding a desktop could ever reach terminal CANCELLED.

Nothing failed. Module 04's tests passed because they acknowledged at epoch 0, which matched. The gap
only became visible when something actually issued an epoch.

`admit_to_desktop` is the missing reducer and `admit_lease` applies it in the transaction that grants
the lease.

### What the last two rows mean, and what was done about them

The advisory lock surviving its own removal is the interesting result. It was described in the module
docstring as the ergonomic half of a two-layer design; mutation showed it was neither half of
anything. `admit_lease` already takes `SELECT ... FOR UPDATE` on the runner row, which serializes
every contender for the same desktop, and the unique-violation branch produces the same `SessionBusy`
the lock's own check would have raised.

So the lock was removed rather than retained with a note. The one case a per-runner row lock does not
cover is two runner rows sharing a desktop, reachable only by revoking a runner mid-lease and
re-enrolling the same screen — and that window is now closed where it starts: `revoke_runner` refuses
while a lease is active. Three tests cover the new guard, and it immediately caught one of this
module's own tests that had been revoking straight through a live lease.

Module 04's handoff recorded the same confound — an advisory lock indistinguishable from a unique
index. Keeping it here would have repeated a mistake that was already written down.

One mutant in this set was initially invalid: the first attempt at "journal the intent after dispatch"
moved the write to a line that was still before the dispatch call, so nothing reordered and no test
failed. Re-run with the write actually after the `await`, it failed two tests. A mutant that does not
change behaviour proves nothing about the tests.

## A window found by mutation rather than by review

`revoke_runner` previously retired a registration while it still held a live lease. The consequence
was not a broken invariant — the unique index still refuses a second lease on that `session_key` —
but it created the only state in which two runner rows can name one desktop, and therefore the only
state in which the per-runner row lock serializes nothing.

It was visible only because removing the advisory lock failed no tests, which prompted the question
of what the lock was for.

## Three gaps found in a self-review, after CI was green

The automated reviewer was rate limited on this pull request, so the independent-review step was done
by hand over the new code. It found three things, all of which CI had been perfectly happy with.

**`revoke_runner` retired a registration holding a live lease** — described above; found by asking
what the advisory lock was for.

**The ambiguity constraint was one-directional.** `ambiguity_reason IS NULL OR result_status =
'AMBIGUOUS'` permits an AMBIGUOUS action with no reason recorded, which is the worst of the three
states: it reads as a known-bad result in any query filtering on status while telling an operator
nothing about what is unknown. It is also exactly the state a caller reaches by writing the row
directly rather than through `mark_action_ambiguous` — which is the function that quarantines the
desktop. Now `(ambiguity_reason IS NOT NULL) = (result_status = 'AMBIGUOUS')`.

**`record_action_intent` trusted the caller's epoch.** Nothing in the schema could catch a mismatch:
the foreign key binds the lease, not its epoch. An action journaled under the wrong epoch is an action
nobody can attribute to a session, which is the entire purpose of recording the epoch. It is now read
from the lease and compared, and a released lease is refused outright — an action against a released
lease is work attributed to a session that had already ended.

That last guard immediately failed one of this module's own tests, which had been journaling a second
action after the first one released the lease. Two guards in this module have now caught this
module's own tests, which is the argument for writing them.

## A window found by a test rather than by reasoning

In the supervisor, `inFlight` was set *after* the journal flush. The flush is real I/O, so a
cancellation arriving during it found nothing unresolved and `mayAcknowledgeStop()` returned `true` —
reporting a clean stop for a keystroke that was about to be dispatched. The assignment moved before
the flush: the supervisor is committed to an action from the moment it decides to journal it, so that
is when the state must say so.
