## Scope and exact state

Implemented: the runner registry, enrollment with single-use workspace-bound credentials, structured
preflight, transactional lease admission keyed on the physical interactive desktop, the pre-dispatch
revalidation, the supervisor action gate, the durable local action journal, cancellation and stop
proof, quarantine, and operator reset and inspection.

**Not implemented, and this is the whole of what module 07 cannot do:** no screen reader has been
driven. There is no VoiceOver adapter (module 08) and no NVDA adapter (module 09), so the supervisor's
`dispatch` callback has nothing behind it. The binary refuses to start and says so, rather than coming
up and reporting itself healthy — a runner that did that would be enrollable, leasable and incapable
of producing a single reader observation.

## The interfaces modules 08 and 09 must implement

Module 07 deliberately stops at one seam. A screen-reader adapter supplies exactly this:

```ts
dispatch: (command: ActionCommand) => Promise<'SUCCEEDED' | 'FAILED'>
```

Four properties of that contract are load-bearing for the adapters:

1. **It may reject or never settle.** Both are treated identically — `AMBIGUOUS`, desktop fenced. An
   adapter must not convert "I lost the channel" into `FAILED`, because a rejected promise is not
   evidence the operating system did nothing.
2. **It is called at most once per `actionId`.** There is no retry anywhere in the protocol. An
   adapter that retries internally is breaking INV-09 on the supervisor's behalf.
3. **It is called only after the intent is on disk.** The adapter can rely on that: if it is running,
   a durable record of the request already exists.
4. **It does not decide readiness.** The adapter supplies observations for
   `PreflightCheck.READER_ACTIVE`, `SPEECH_CAPTURE_WORKING`, `NO_STALE_INPUT_SOURCE` and the
   permission checks; the server concludes READY. There is no field an adapter can set to say it is
   ready.

The fourteen `PreflightCheck` values are the closed vocabulary an adapter reports into. Adding one is
a deliberate edit to `REQUIRED_PREFLIGHT_CHECKS`, in one place, visible in a diff — because adding a
check to the enum without adding it there would create an optional proof of desktop safety.

## The lease lifecycle

```
                      enroll (single-use token)
                               |
                               v
OFFLINE  <------------>  PREFLIGHT_REQUIRED  <-------------------+
   |                           |                                 |
   |                    successful preflight                     |
   |                           v                                 |
   |                        READY ---- admit_lease ----> BUSY     |
   |                           |        (epoch N+1)       |       |
   |                           |                          |      stop acknowledged
   |                           |                          |      for epoch N+1,
   |                           |                          |      no unresolved action
   |                           |                          +-------+
   |                           |
   +------------> QUARANTINED <+---- expiry without stop proof
                     |               ambiguous action
                     |               failed preflight / profile drift
                     |               failed reset / operator request
                     |
              successful reset (fences epoch N)
                     |
                     v
            PREFLIGHT_REQUIRED
```

Two edges do not exist, and their absence is the design:

- **QUARANTINED → READY.** A fenced desktop re-proves itself or stays fenced. Reset proves the old
  session is dead; preflight proves the new one works; they are separate facts.
- **BUSY → READY.** The browser is wherever the finished run left it, so readiness is re-established
  rather than assumed.

## Crash, cancel and expiry results

| Situation | Lease | Runner | Run | Why |
|---|---|---|---|---|
| Cancellation requested | active, `cancel_requested_at` set | BUSY | **RUNNING** | Nothing has established that the desktop stopped. Only new work is fenced. |
| Stop acknowledged, current epoch, nothing unresolved | released `STOP_ACKNOWLEDGED` | PREFLIGHT_REQUIRED | CANCELLED / INCONCLUSIVE | Proof. Outcome is INCONCLUSIVE because execution had begun. |
| Cancellation on a never-leased run | none ever existed | — | CANCELLED / NOT_EVALUATED | Provably never admitted to a desktop, so provably unable to have typed. |
| Stop acknowledged from a superseded epoch | unchanged | unchanged | unchanged | An earlier session's acknowledgement says nothing about the current one. |
| Acknowledgement while an action is unresolved | unchanged | unchanged | unchanged | The supervisor stopped *asking*. The keystroke may still have landed. |
| Lease deadline passes | released `EXPIRED_WITHOUT_STOP_PROOF` | **QUARANTINED** | unchanged | A silent supervisor is not a stopped supervisor. |
| Action result never arrives | released `AMBIGUOUS_ACTION` | **QUARANTINED** | INTERRUPTED / INCONCLUSIVE, `ambiguityReason` | Unknown, and not re-dispatched (INV-09). |
| Supervisor crashes after intent | — | quarantine required | INTERRUPTED | The journal says an action was intended and its result is unknown. |
| Reset fails | released `SUPERSEDED_BY_RESET` | **QUARANTINED** `RESET_FAILED` | unchanged | Failing to prove the old actor cannot act is not proof that it can't. |
| Reset succeeds | released `SUPERSEDED_BY_RESET` | PREFLIGHT_REQUIRED | unchanged | Old session dead. New session unproven. |

## The reset contract

`reset_runner` is the only door out of quarantine. It takes `succeeded` from the trusted reset
procedure — never from the runner — and records a proof document plus this warning, verbatim, with
every reset:

> A reset acts on one physical interactive desktop session. It closes the browser profile and
> restarts the supervisor and the screen reader within that session only. It does not kill processes
> outside the runner's own session, and it must not be performed on a desktop someone is using:
> anyone signed in to it will lose unsaved work in the affected applications.

`inspect_runner` returns the active lease, the unresolved actions, the ambiguous actions and that same
warning, because "is anything still in flight" is what decides whether a reset is an inconvenience or
an interruption of something in progress.

## A gap between modules 04 and 07

`lease_epoch` was on `RunState` and on the `run` row from module 04, was written by every transition,
and was never *set* by anything — no reducer took an epoch. A run's epoch stayed `0` for its whole
life, so `acknowledge_stop`, which refuses an acknowledgement whose epoch does not match the current
one, would have refused **every acknowledgement that could ever exist**. A stop could never be proved;
no run holding a desktop could ever reach terminal CANCELLED.

Nothing failed. Module 04's tests passed because they acknowledged at epoch 0, which matched. The gap
only became visible when something actually issued an epoch.

`admit_to_desktop` is the missing reducer and `admit_lease` applies it in the transaction that grants
the lease.

### What the last two rows mean, and what was done about them

The advisory lock surviving its own removal is the interesting result. It was described in the module
docstring as the ergonomic half of a two-layer design; mutation showed it was neither half of
anything. `admit_lease` already takes `SELECT ... FOR UPDATE` on the runner row, which serializes
every contender for the same desktop, and the unique-violation branch produces the same `SessionBusy`
the lock's own check would have raised.

So the lock was removed rather than retained with a note. The one case a per-runner row lock does not
cover is two runner rows sharing a desktop, reachable only by revoking a runner mid-lease and
re-enrolling the same screen — and that window is now closed where it starts: `revoke_runner` refuses
while a lease is active. Three tests cover the new guard, and it immediately caught one of this
module's own tests that had been revoking straight through a live lease.

Module 04's handoff recorded the same confound — an advisory lock indistinguishable from a unique
index. Keeping it here would have repeated a mistake that was already written down.

One mutant in this set was initially invalid: the first attempt at "journal the intent after dispatch"
moved the write to a line that was still before the dispatch call, so nothing reordered and no test
failed. Re-run with the write actually after the `await`, it failed two tests. A mutant that does not
change behaviour proves nothing about the tests.

## A window found by mutation rather than by review

`revoke_runner` previously retired a registration while it still held a live lease. The consequence
was not a broken invariant — the unique index still refuses a second lease on that `session_key` —
but it created the only state in which two runner rows can name one desktop, and therefore the only
state in which the per-runner row lock serializes nothing.

It was visible only because removing the advisory lock failed no tests, which prompted the question
of what the lock was for.

## A window found by a test rather than by reasoning

In the supervisor, `inFlight` was set *after* the journal flush. The flush is real I/O, so a
cancellation arriving during it found nothing unresolved and `mayAcknowledgeStop()` returned `true` —
reporting a clean stop for a keystroke that was about to be dispatched. The assignment moved before
the flush: the supervisor is committed to an action from the moment it decides to journal it, so that
is when the state must say so.

## Four independent claims

- **Code implemented?** Yes, for everything above the screen reader: enrollment, preflight, lease
  admission, the action gate, the action journal, cancellation and stop proof, quarantine, reset,
  capability matching and pre-dispatch revalidation.
- **Tests passed?** Yes — 1013 Python and 82 Node, on a database created from nothing, with fourteen
  mutations showing the guards are the reason.
- **Real runtime worked?** Real PostgreSQL, real concurrency, a real `fsync`ed journal on disk.
  **No screen reader has run. No operating-system fencing has been demonstrated.** A lease is a row;
  whether it actually prevents another process from sending input to that screen is unproven here.
- **Release ready?** No.
