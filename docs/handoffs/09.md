## Whether module 25 may count the NVDA benchmark as executed

The prompt asks for this by name. **No.**

It is exported as a constant, `MODULE_25_MAY_COUNT_NVDA_BENCHMARK = false`, with a test asserting it,
rather than left as a sentence in a document. A benchmark table with an NVDA row that was never run
outlives the caveat printed beside it, and module 25 should have to change a value in code to claim

## Why this is blocked more completely than module 08

Module 08 runs on the platform it targets and needs settings changed. Module 09 has **no Windows
machine at all** — not one missing NVDA — and no virtualization software on this host to run one.
The blocker is hardware or a VM licence, not a checkbox.

Per the stop condition — "finish only independent adapter/contract work and mark real integration
BLOCKED" — that is exactly what this module contains.

## What was built, and what was deliberately not copied

The prompt says to share protocol contracts with module 07 "not platform-specific assumptions copied
from VoiceOver". Three things differ, and none of them is cosmetic:

**Chords.** VoiceOver navigates with `CTRL+OPT+ARROW`; NVDA uses browse-mode arrows and the NVDA
modifier. A copied list would be simultaneously too permissive — allowing macOS combinations Windows
maps elsewhere — and useless, omitting the keys NVDA actually needs. The refusal list differs too:
`F12`, `WIN+R` and `ALT+F4` matter here; `CMD+L` means nothing.

`CTRL+ALT+DEL` is listed with the note that Windows intercepts it before any application sees it.
That is the clearest available argument for an allowlist: **a denylist cannot block what never
reaches it.**

**A different unusable-desktop problem.** macOS worries about a locked screen. Windows worries about
that *and* about `RDP_SESSION_DISCONNECTED`, which has no macOS equivalent and is the dangerous one:

> A disconnected Remote Desktop session keeps running. Processes execute, the automation API responds,
> and there is no console attached to receive input. Automation returns success and nothing reaches a
> screen, so the run produces an empty trace — which module 11 reads as a missing announcement and
> therefore as an accessibility failure.

`SESSION_IS_A_SERVICE_SESSION` is listed for the same reason: session 0 has no interactive desktop,
and a background service is not automatically a usable desktop however healthy it reports itself.

`desktopIsUsable(undefined)` **fails closed**. That is the call a caller makes when its probes have
not run, and every state in the list is invisible from outside the session it describes.

**Cross-reader comparison is by assertion, never by transcript.** VoiceOver might say "Email, invalid
data, edit text" where NVDA says "Email edit invalid entry". Both are correct announcements of the
same correct page. Requiring the strings to match would fail every correct Windows page, and would
push someone to normalize NVDA's wording into VoiceOver's — which is manufacturing an observation.
`CROSS_READER_COMPARISON_RULE` states this and a test asserts it.

## Shared protocol compatibility

The action vocabulary is module 07's eight values, asserted by test rather than restated. The adapter
seam is the same `dispatch(command) => Promise<'SUCCEEDED' | 'FAILED'>` module 07's handoff specified,
with the same four properties: it may reject or never settle, it is called at most once per action id,
it is called only after the intent is on disk, and it does not decide readiness.

Nothing Windows-specific reaches the outcome rules. There is no separate Windows outcome path, and
module 10 ingestion is the shared event protocol.
