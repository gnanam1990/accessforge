# Handoff 19 — Durable event streams and bounded schedules

- **Module:** 19. **Requirements:** FR-014, FR-015, FR-019, FR-021
- **Invariants:** INV-06, INV-07, INV-08, INV-11, INV-13

## Transport

**Local and proposed hosted: PostgreSQL is the transport.** The outbox from module 04 is the queue;
`outbox_message.id` is the cursor; delivery is a read over that table. No message broker is
introduced, locally or in the hosted proposal.

The reason is not simplicity. A broker would become a second place where an event exists, and
"published to the broker" and "committed to PostgreSQL" would be two facts that can disagree. With
the outbox as transport there is exactly one, and the module prompt's rule — neither transport
becomes the authoritative source of business state — is satisfied by there being nothing else to
mistake for it.

Server-sent events are the wire format. `id:` carries the cursor, which a browser echoes back in
`Last-Event-ID` on reconnect with no application code. The resume contract is part of the protocol
rather than something every client reimplements.

## The cursor is an integer, never a timestamp

`outbox_message.id` is a BIGSERIAL assigned in commit order. Two events committed in the same
microsecond are indistinguishable by time, so a resume that skipped everything at-or-before a
timestamp cursor would drop one — and keep dropping for the rest of that connection, with nothing to
notice.

A structural test asserts the parameter's type. Its first version compared the annotation to `int`
and failed because `from __future__ import annotations` makes it the string `"int"`; the assertion
now compares the string, and the reason is recorded in the test.

## A replay gap is a reset, not a short page

A cursor below the retention floor raises `ReplayGap` pointing at the snapshot. Serving what remained
would leave a client believing it had seen everything since its cursor — the one thing a resume must
not get wrong.

The boundary is exact and tested both ways: a cursor **equal to** the floor is accepted (the client
saw that event and wants what came after); only a cursor strictly below it is a gap. Getting that
comparison backwards would either reject every correct resume at the edge or serve truncated ones.

The retention floor never moves backwards, so a late worker cannot re-open a window already declared
closed.

## Reconnection never implies completion

The failure this guards: a client reconnects, receives no further events, and concludes the run
finished. `test_an_empty_stream_says_nothing_about_completion` reconnects to an empty stream and
asserts the snapshot still reports the run QUEUED and NOT_EVALUATED.

A snapshot carries **the cursor it was taken at**, and both are read in one transaction. Taken
separately, an event committed between them would be applied twice or missed depending on timing
nobody controls.

Events carry **references, not state**. An event containing the state itself would be state with no
revision check, delivered at least once, arriving out of order after a reconnect.

## Progress is durable and never rewinds

`processed_through` advances with `GREATEST`, after the work is durable and never before. A publisher
restart therefore re-delivers, which consumers are built for; the alternative loses a committed event,
which nothing recovers from. A stale worker writing after a newer one cannot rewind the position.

## Schedules cannot broaden their grant

A schedule pins the **grant revision** it was approved against, and every occurrence rechecks
revocation, revision, expiry and scope. Four separate refusals are tested: revoked, revised,
narrowed, and expired. A grant revised since approval is a different decision, and following the
reference would run under terms nobody approved.

A journey outside the grant's allowed set is refused **at creation**, not at the first occurrence.
Discovering it later means somebody already believed it was approved.

A schedule cannot outlive its grant, and a timezone is required — without one a schedule runs at a
different wall-clock hour twice a year, and "it fired an hour late in March" is a bug nobody
reproduces in July.

`assert_grant_cannot_authorize` refuses PATCH_APPLY and GITHUB_PUBLISH by name. Scopes do not nest: a
grant to run a test repeatedly is not permission to change code, however many times it has been used.

## One occurrence, one run

A unique key on `(schedule_id, scheduled_for)` — the *scheduled* instant, not when work started.
Keying on the latter would let two workers a millisecond apart both believe they owned the occurrence.

A missed window is **skipped with a reason**, never replayed as a burst. A service down for six hours
does not wake and fire six runs at a desktop that holds one attempt, and a run six hours late tests a
source ref and an environment that have both moved on.

Overlapping occurrences are skipped for the same reason: INV-10 means one attempt per desktop, so
overlap would queue and arrive as a burst rather than a schedule.

Every occurrence produces a row — admitted with a run, or skipped with a reason — enforced by a check
constraint. An occurrence that simply left no trace is indistinguishable from one the scheduler never
noticed, and the difference is what an operator is trying to establish.

Pausing keeps the schedule and records who paused it. Deleting loses the fact that it existed and
that somebody turned it off.

## What is not proved

**No SSE endpoint is exposed yet.** The stream primitives, the resume contract and the snapshot are
implemented and tested at the persistence layer; module 18's route surface does not carry a
`/v1/.../events/stream` route. The acceptance gate asks for a browser reconnecting after a real
API/worker interruption, and there is no browser — module 21 is the UI foundation and does not exist.
So the reconnect behaviour is proved against the primitives and **not** end to end.

**Schedule runtime proof is BLOCKED.** The gate for R1 asks for one authorized schedule running once
per admitted occurrence with a real runner. There is no real runner: modules 08 and 09 are blocked.
Every occurrence in these tests created a run record that nothing executed.

**No recurring automation is installed outside the product.** No cron entry, no launchd job, no
external scheduler. `admit_occurrence` is called by a caller; nothing here installs a timer on the
host.
