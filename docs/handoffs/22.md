## What an operator can now do

Configure a project, authorize an environment, author and freeze a journey version, read the runner
inventory, and request one explicitly authorized run — all against the real API, with the result in
PostgreSQL.

Five screens replaced their not-built placeholders: overview, projects, one project, one journey
version, and runners. The remaining six (`runs/:runId`, findings, patches, reviews, exports,
settings) still say which module owns them and request nothing, because they still do not exist.

## The routes this module had to add

Module 18 exposed a read route for a journey version and nothing that wrote one. Every journey in
this system had been inserted by a test. Rather than have the UI invent something, this module built
the writer and the routes:

| Route | Why |
|---|---|
| `POST /journeys` | Compile a draft through module 06 and seal it. There is no edit route and cannot be: a trigger refuses every UPDATE |
| `GET /projects/{id}/journeys` | Versions with their lineage |
| `GET /journeys/{id}/policy` | Exactly what the navigator will be given |
| `GET /journey-capabilities` | The domain's own allowlists, so the form is not a second copy of the policy |
| `POST,GET /projects/{id}/environments` | The authorized scope, and why an unusable one is unusable |
| `GET /runners` | The inventory, with the evidence behind each status |
| `GET /members` | So "who authorized this" can be a person rather than a typed string |

`packages/persistence/.../journeys.py` compiles through `compile_journey` and stores what it
returns. No digest is computed there — a digest computed in the writer would be a second
implementation of the seal, and the second one drifts.

## The decisions that carry the module

**Freezing is not running.** The button says "Freeze version"; the confirmation says the version is
sealed and authorizes nothing to execute. Requesting a run is a separate action behind a dialog that
shows the four digests in full and names its scope as `RUN_EFFECTS`.

**Editing produces a successor.** `supersedes` is carried on the new version, the predecessor is
unchanged, and runs already sealed against it keep it. A successor cannot name a version from
another project: the composite foreign key already prevents crossing a workspace, and the writer
prevents crossing a project inside one — otherwise a journey's history would depend on a project the
reader may not be able to see.

**Superseded is computed across the project, not the page.** A successor on a later page would leave
a stale version looking current, and current is what an operator runs.

**Unsupported and invalid are different answers.** A `CapabilityError` is 422 with the domain's own
capability code and renders as "AccessForge cannot do what this journey asks"; a `JourneyError` is
400 naming the field and lands in the error summary, linked to the control. Collapsing them would
tell an author to fix their typing when the real answer is that the capability does not exist.

**A runner row is never readiness.** `preflightPassedAt` is its own column, `null` renders as
"Never" in words rather than as a blank, and the server's statement — that READY is not inferred
from the runner process being reachable, and that no status is evidence a journey will pass — is
shown on the page rather than summarised away. INV-02 turns on this, and a list is the first place
that inference gets made.

**The unsupported matrix is on the screen.** macOS VoiceOver is listed as *not verified* on this
installation; Windows NVDA as *unavailable* because module 09 does not exist; mobile and PDF as out
of scope. A screen offering three profiles without saying which are verified invites an operator to
choose one that cannot run.

**Authorizing an environment is not a connection test.** Stated above the form. The observer and
reset credential references must differ, and the refusal says why: one identity that can both set up
the answer and attest to it is not an independent observer. No credential value is accepted, stored,
digested or exported — only references, and the listing shows neither.

**Unusable is never a bare flag.** Expired, revoked and superseded are named separately, because
they lead an operator to three different actions.

## Two defects a real browser found

**A person's name in "Authorized by" produced a 500.** The column is a UUID referencing a real user,
and a name reached the driver as a raw string: an unhandled error, a stack trace in the log, and
nothing useful for the caller. The fix is in two parts. `create_project` now refuses a
non-identifier with a 400 that says a name is not a record of who granted permission, and requires
the authorizer to hold a live membership in this workspace — an authorization recorded against
somebody the workspace cannot name is not auditable, and requiring membership also removes the
account-existence oracle that checking `app_user` alone would have created. The form is now a picker
of real members, because a field asking for a raw identifier is a field nobody can fill in.

That change broke one existing fixture, which had been recording an authorizer with no membership.
The database accepted it because the column only references `app_user`. The fixture now creates the
membership, which is what it always meant.

**The double-click guard was unreachable.** The run confirmation held a synchronous re-entry ref
alongside the disabled-while-busy button. A mutation check showed nothing could reach the ref:
React flushes a discrete event's state update synchronously, so the second half of a double-click
arrives at a button that is already disabled and produces no event at all. The ref was removed — a
guard nothing can reach is worse than no guard, because it invites the reader to believe the danger
is handled somewhere else. What does the work is the disabled button, plus an idempotency key
generated when the dialog opens and cleared when it closes.

Three of the first attempts had to be rewritten, and two of those exposed vacuous tests: the

delete the ref rather than to write a test that could not fail honestly.

## What is not proved

**No run has executed.** A run reaches `QUEUED` and stops there, because no runner can pass a
preflight: VoiceOver is unconfigured on this host and module 09 does not exist. Everything downstream
of dispatch — admission, action fencing, evidence, a verdict — is untested by this module and stays
untested until a real reader exists. The acceptance gate asks for the reference application's real
form-error recovery task to be configured, the actual supported runner inspected, and one authorized
run dispatched. The first two are done against real data. The third is **requested, not dispatched**,
and the screen says so in those words.

**Several of the prompt's tasks have no backend to talk to.** Durable event integration in the UI
(there is no SSE route; module 19 built the primitives), schedule setup and `ExecutionGrant`
previews (no routes), source and build binding on the project screen (module 05's persistence has it,
no route exposes it), and the Strands "Suggested draft — review required" labelling (module 12 does
not exist). None is simulated with local browser state, and none is presented as present-but-empty.

**Cancellation has a screen but no run to cancel.** The route exists and module 18 tested it;
module 23 owns the run detail screen where it belongs. Nothing in module 22 claims a cancellation
was acknowledged.

**No actual screen reader was used**, and no automated accessibility scan is included — same
position as module 21, for the same reasons. The keyboard flows here were driven programmatically
in a real browser: focus lands on the error summary on every failed submission, every summary entry
resolves to a real control, and the run confirmation is reachable and operable. That is not the
same as somebody listening to it.
