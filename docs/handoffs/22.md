## What an operator can now do

Configure a project, authorize an environment, author and freeze a journey version, read the runner
inventory, and request one explicitly authorized run — all against the real API, with the result in
PostgreSQL.

Five screens replaced their not-built placeholders: overview, projects, one project, one journey
version, and runners. The remaining six (`runs/:runId`, findings, patches, reviews, exports,
settings) still say which module owns them and request nothing, because they still do not exist.

## The routes this module had to add

Module 18 exposed a read route for a journey version and nothing that wrote one. Every journey in
this system had been inserted by a test. Rather than have the UI invent something, this module built
the writer and the routes:

| Route | Why |
|---|---|
| `POST /journeys` | Compile a draft through module 06 and seal it. There is no edit route and cannot be: a trigger refuses every UPDATE |
| `GET /projects/{id}/journeys` | Versions with their lineage |
| `GET /journeys/{id}/policy` | Exactly what the navigator will be given |
| `GET /journey-capabilities` | The domain's own allowlists, so the form is not a second copy of the policy |
| `POST,GET /projects/{id}/environments` | The authorized scope, and why an unusable one is unusable |
| `GET /runners` | The inventory, with the evidence behind each status |
| `GET /members` | So "who authorized this" can be a person rather than a typed string |

`packages/persistence/.../journeys.py` compiles through `compile_journey` and stores what it
returns. No digest is computed there — a digest computed in the writer would be a second
implementation of the seal, and the second one drifts.

## The decisions that carry the module

**Freezing is not running.** The button says "Freeze version"; the confirmation says the version is
sealed and authorizes nothing to execute. Requesting a run is a separate action behind a dialog that
shows the four digests in full and names its scope as `RUN_EFFECTS`.

**Editing produces a successor.** `supersedes` is carried on the new version, the predecessor is
unchanged, and runs already sealed against it keep it. A successor cannot name a version from
another project: the composite foreign key already prevents crossing a workspace, and the writer
prevents crossing a project inside one — otherwise a journey's history would depend on a project the
reader may not be able to see.

**Superseded is computed across the project, not the page.** A successor on a later page would leave
a stale version looking current, and current is what an operator runs.

**Unsupported and invalid are different answers.** A `CapabilityError` is 422 with the domain's own
capability code and renders as "AccessForge cannot do what this journey asks"; a `JourneyError` is
400 naming the field and lands in the error summary, linked to the control. Collapsing them would
tell an author to fix their typing when the real answer is that the capability does not exist.

**A runner row is never readiness.** `preflightPassedAt` is its own column, `null` renders as
"Never" in words rather than as a blank, and the server's statement — that READY is not inferred
from the runner process being reachable, and that no status is evidence a journey will pass — is
shown on the page rather than summarised away. INV-02 turns on this, and a list is the first place
that inference gets made.

**The unsupported matrix is on the screen.** macOS VoiceOver is listed as *not verified* on this
installation; Windows NVDA as *unavailable* because module 09 does not exist; mobile and PDF as out
of scope. A screen offering three profiles without saying which are verified invites an operator to
choose one that cannot run.

**Authorizing an environment is not a connection test.** Stated above the form. The observer and
reset credential references must differ, and the refusal says why: one identity that can both set up
the answer and attest to it is not an independent observer. No credential value is accepted, stored,
digested or exported — only references, and the listing shows neither.

**Unusable is never a bare flag.** Expired, revoked and superseded are named separately, because
they lead an operator to three different actions.

## Two defects a real browser found

**A person's name in "Authorized by" produced a 500.** The column is a UUID referencing a real user,
and a name reached the driver as a raw string: an unhandled error, a stack trace in the log, and
nothing useful for the caller. The fix is in two parts. `create_project` now refuses a
non-identifier with a 400 that says a name is not a record of who granted permission, and requires
the authorizer to hold a live membership in this workspace — an authorization recorded against
somebody the workspace cannot name is not auditable, and requiring membership also removes the
account-existence oracle that checking `app_user` alone would have created. The form is now a picker
of real members, because a field asking for a raw identifier is a field nobody can fill in.

That change broke one existing fixture, which had been recording an authorizer with no membership.
The database accepted it because the column only references `app_user`. The fixture now creates the
membership, which is what it always meant.

**The double-click guard was unreachable.** The run confirmation held a synchronous re-entry ref
alongside the disabled-while-busy button. A mutation check showed nothing could reach the ref:
React flushes a discrete event's state update synchronously, so the second half of a double-click
arrives at a button that is already disabled and produces no event at all. The ref was removed — a
guard nothing can reach is worse than no guard, because it invites the reader to believe the danger
is handled somewhere else. What does the work is the disabled button, plus an idempotency key
generated when the dialog opens and cleared when it closes.

## Fourteen more, from the independent review

CodeRabbit reviewed the first commit. Thirteen findings were real and are fixed; one is recorded as
declined. The largest changes what the module claims.

**The run request was sending a journey digest where a sealed manifest digest belongs.** A run's
identity is the sealed manifest: the source commit, the built artifact, the environment
configuration, the journey, its assertions and fixture, the runner profile, the evaluator version
and the model configuration — together. A journey digest names none of that. Every run this module
queued during its first verification pass carried an identity that matched nothing, and dispatch
would later have refused it for naming a different sealed manifest.

The fix is not a different digest; there is no sealed manifest to send. Sealing needs a source
snapshot and a build artifact, and nothing exposes a route to record either. So the journey screen
now reads the project's sealed manifests and, finding none, **refuses to request a run** — with the
reason and the missing prerequisites on the page. That is task 8 of this module's own prompt, which
the first version had glossed: a disabled run control with an accessible explanation and a safe next
step. Assembling a plausible digest was the failure; a control that explains why it cannot act is
the fix.

**The idempotency key was discarded when the server did not answer.** `offline` means the request
may well have arrived and the answer been lost. Clearing the key and generating a fresh one on the
next attempt would turn one authorization into two runs — precisely what the key exists to prevent.
The dialog now stays open, the key is kept, and the notice no longer claims nothing was changed,
because this client cannot know that.

The other eleven:

| Finding | Why it mattered |
|---|---|
| `str()`, `bool()` and `int()` coerced request values | `null` became the string `"None"`, `"false"` became `True`, `1.9` became `1` — and a journey version is immutable, so a coerced value is coerced forever |
| Supersession failures named `projectId` | The message was about the predecessor and the highlighted control was the project |
| Identifiers reached PostgreSQL unvalidated | `invalid input syntax for type uuid` is an unhandled driver error and a 500, on values that arrive from a request body |
| A disabled account could authorize a repository | A membership row survives its account being disabled, so the API refused to *offer* a person it would then accept |
| The environment listing took 200 rows with no cursor | A project with more lost the older ones silently, including usable ones, under a heading claiming to be the inventory |
| Listings rendered one page as a complete inventory | Same claim, on the client side; all five now follow the cursor and say so when they stop early |
| Budget fields were converted without validation | `Number('')` is 0 and `Number('1e')` is `NaN`, which `JSON.stringify` writes as `null` |
| Blank credential references were reported as equal | Two blanks *are* equal, so the refusal was accurate about the comparison and wrong about the cause; one blank passed the domain and was stored empty |
| `readerVersion: null` rendered the word "null" | `=== undefined` is false for null |
| A failed member list left an empty picker and no reason | The form insists a repository names an authorizer, and the error pointed at a control with no options |
| The fake server was typed `Record<string, unknown>` | A fixture missing a field the screen reads fails for a reason unrelated to the test |

**Declined: explicit OpenAPI schemas for the new operations.** The finding is correct — every route
handler in this repository takes and returns `dict[str, Any]`, so the generated contract describes
unrestricted objects and omits the RFC7807 responses. It is also a property of all 32 routes, set by
module 18, not something these seven introduced. Changing it is a contract-wide piece of work that
belongs to a module that owns the API surface, and doing it here would leave the codebase with two
conventions. Recorded rather than half-done.

## What is not proved

**No run can be requested at all, and that is the corrected position.** The first version of this
module queued runs against a journey digest, which is not a manifest identity. With that removed,
requesting a run needs a sealed manifest; sealing needs a recorded source snapshot and a build
artifact; and no route records either. So the acceptance gate's third clause is not met, and the
screen says why rather than substituting a value. Even with a manifest, a run would reach `QUEUED`
and stop: no runner can pass a preflight, because VoiceOver is unconfigured on this host and module
09 does not exist. Everything downstream
of dispatch — admission, action fencing, evidence, a verdict — is untested by this module and stays
untested until a real reader exists. The acceptance gate asks for the reference application's real
form-error recovery task to be configured, the actual supported runner inspected, and one authorized
run dispatched. The first two are done against real data. The third is **requested, not dispatched**,
and the screen says so in those words.

**Several of the prompt's tasks have no backend to talk to.** Durable event integration in the UI
(there is no SSE route; module 19 built the primitives), schedule setup and `ExecutionGrant`
previews (no routes), source and build binding on the project screen (module 05's persistence has it,
no route exposes it), and the Strands "Suggested draft — review required" labelling (module 12 does
not exist). None is simulated with local browser state, and none is presented as present-but-empty.

**Cancellation has a screen but no run to cancel.** The route exists and module 18 tested it;
module 23 owns the run detail screen where it belongs. Nothing in module 22 claims a cancellation
was acknowledged.

**No actual screen reader was used**, and no automated accessibility scan is included — same
position as module 21, for the same reasons. The keyboard flows here were driven programmatically
in a real browser: focus lands on the error summary on every failed submission, every summary entry
resolves to a real control, and the run confirmation is reachable and operable. That is not the
same as somebody listening to it.

## Addendum — schedules and standing authorizations (built after module 27)

Module 19 built the domain and module 18's completion added ten routes; neither gave them a screen,
so a standing grant could be created and recovered only from a terminal. This closes that.

**It is a settings section, not a route.** The first version added `/w/:workspaceId/schedules`, and
the route-table test failed immediately — UI-UX section 3 puts schedules under `/settings`
("Membership, integrations, retention, budgets, schedules and manual entitlement"). Adding a path the
specification does not list is exactly what module 21's acceptance gate forbids, and the three tests
that caught it are the ones holding the router, the sidebar and the spec together. They did their
job.

### What the screen refuses to collapse

| | |
|---|---|
| **Three grant states, not two** | "Awaiting revalidation" is neither usable nor revoked: nobody withdrew it, and nobody can vouch for it either. Collapsing it into "revoked" loses the difference between a decision and the absence of one. |
| **`usable` comes from the server** | Not re-derived here. A screen with its own idea of usability eventually disagrees with the code that enforces it, and the disagreement appears as a grant the page calls usable and every run refuses. |
| **Revoked grants and paused schedules stay listed** | "What was allowed to run, and when did that stop" needs both halves, and a paused schedule that vanished would look deleted. |
| **Both grant revisions are shown** | "approved at 1, now 3" is the comparison that explains a schedule which has quietly stopped. Showing only one number hides either the reason or what was actually approved. |
| **A grant that cannot be read is not a revoked grant** | "Grant not visible" is its own state. Presenting it as revoked would invent a decision nobody made. |
| **No creation form** | Both carry bounds on every axis and nine input digests. A browser form would produce a plausible authorization rather than a correct one; the screen says so instead of leaving a reader hunting for the button. |

### The recovery, kept to two deliberate steps

Reconciliation marks every restored grant as needing revalidation *and* moves its revision, which
also stops every schedule bound to it. Confirming the grant does **not** restart the schedules, and
the screen enforces that shape: while a grant is unusable its schedules offer no re-approval at all
(doing it first cannot work, and offering it would invite an operator to be refused), and the
schedule's own control appears only once the grant is usable and the revision has moved.

Driven end to end in a real browser against the real API and real PostgreSQL:

1. Revoked a grant → state `Revoked`, revision 1→2, the server's reason verbatim, Revoke control
   gone, and its schedule immediately `Stopped — grant unusable`.
2. Marked the other grant as a restore leaves it → `Awaiting revalidation`, both schedules stopped,
   **no** re-approval offered anywhere.
3. Confirmed the grant → `Usable`, revision 2→3. The schedule did not resume: it moved to
   `Stopped — grant moved` (approved at 1, now 3) and only then offered `Re-approve`.
4. Re-approved → `Active`, approved at 3, now 3.

### A defect in my own test helper

Two of the seventeen tests failed for a reason that had nothing to do with the screen: the
`schedule()` fixture factory was missing `...overrides`, so every override a test passed was
silently discarded. One test then asserted against the default fixture instead of the case it named.
Worth recording because a fixture that ignores its arguments fails in the most misleading direction —
the two that broke pointed at the component, and the third would have passed while testing nothing.

### What review found

One finding, and it was real: **every mutation control was rendered for every role.** All five need
`RUN_APPROVE`, which OWNER and MAINTAINER hold and REVIEWER and VIEWER do not — so a viewer saw a
Revoke button that the server answers with 403. A control that exists to fail.

The note also warned against the obvious fix: reusing `MAY_CONFIGURE` from the allowance form. That
set is owner-only, and it would have hidden working controls from a maintainer who genuinely holds
the permission — a quieter failure than offering one that cannot work, and harder to notice.

Gated on OWNER and MAINTAINER, with the rows, states and server reasons still shown in full: an
authorization somebody cannot change is still one they may need to understand.
