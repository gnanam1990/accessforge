# Handoff 17 — Evidence export and the offline verifier

- **Module:** 17. **Requirements:** FR-013, FR-014, FR-015, FR-020
- **Invariants:** INV-03, INV-06, INV-11, INV-12, INV-15

## Three claims, kept apart

An export is where evidence leaves the system, and the question that shapes the format is not what to
include but what a reader can conclude. Three claims are routinely collapsed into one, so nothing here
lets them merge:

1. **The bytes are intact.** Digests match. Checkable by anyone, offline.
2. **The service attests this.** A signature attributing the manifest to an issuer — who assembled
   the bundle, not that what they assembled is true.
3. **A person could use the application.** Established by no bundle, ever.

`TrustLevel` is an enum rather than a boolean, and the verifier returns a list of findings rather than
a verdict. A redacted bundle is not a failed bundle; an unchecked signature is not a passed one; a
bundle in an unknown format is neither.

## The verifier runs with nothing

`accessforge-verify bundle.zip --trust-root trust.json`. No account, no network, no database. Driven
end to end during this module against a bundle built from real PostgreSQL and real MinIO:

```
passed: 12
  - events.chain: 4 events, contiguous from 1, hashing to the manifest digest
  - producers.watermarks[observer:receipts]: closed at 1, matching the admitted tail
  - artifacts.digests[SPEECH_TRANSCRIPT]: included bytes hash to the declared digest (RETAINED)
  - identities.bound: 8 identities bound, including every one INV-03 requires
  - attestation.signature: attributed to accessforge-service using key af-cli-demo, which you
    supplied independently of this bundle
Trust level: FULLY_VERIFIABLE
```

Exit code 0. Every failed integrity check produces exit 1.

## An embedded public key is not provenance

The check that decides whether a signature means anything. A forger signs with their own key, embeds
it, and recomputes every digest — so all of them match. The signature verifies.

`KeyProvenance` distinguishes the case, and the report says:

> self-consistent signature by key af-…, which travelled inside the bundle. This attributes the
> bundle to nobody: a forger signs with their own key and embeds it.

`test_a_key_from_inside_the_bundle_attributes_nothing` asserts `integrity_intact` is **true** and
`independently_trusted` is **false** in the same test — the bytes really are intact, and that is not
the question.

Results are phrased as **attribution** rather than validity throughout. A reader who sees "signature
valid" concludes the contents are true. A reader who sees "attributed to X using a key you supplied
out of band" knows what they have, and what they would need for more.

A key-id mismatch is a distinct failure from a bad signature, because they send a reader somewhere
different: a bad signature suggests tampering, a wrong key id usually means an intact bundle and the
wrong key.

## The signed bytes must be the manifest shown

A bundle could carry a benign readable `bundle.json` and signed canonical bytes describing something
else. The signature would verify, the human would read the wrong document, and every other check would
examine the one that was not signed. `manifest.signedBytes` compares them.

## Contiguity is not completeness, again

`test_a_missing_observer_watermark_makes_the_bundle_incomplete` asserts `events.chain` **PASSED** and
the observer's watermark **FAILED** in the same test. The chain has no gaps and half the evidence is
missing.

The test asserts the *message*, not just the outcome. Removing the null check leaves the next branch
failing too — "closed at None but 1 admitted" — so an outcome-only assertion could not tell the two
apart, and the explanation an operator reads is the whole difference. That mutant survived the first
mutation run and is the reason the assertion changed.

## Four evidence states, never three

`UNAVAILABLE` is separate from `DELETED`. Deleted is a decision somebody made and recorded; unavailable
is a fact about right now. Collapsing them would let an outage read as a retention action, or a
deletion read as something that might resolve itself.

A **redacted** artifact travels as its redacted view with its own digest. Including the raw bytes would
defeat the redaction; excluding it entirely would hide that anything was there.

A **deleted** artifact is reported NOT_APPLICABLE with its reason, and the bundle becomes INCOMPLETE.
INV-15 reaching the export: an artifact that vanished without a note is indistinguishable from one that
never existed.

`evidence_export.retention_snapshot` records what the server held at export time, so an old bundle
never reads as a statement about current retention.

## The issuer writes the trust level; the verifier recomputes it

A bundle claiming FULLY_VERIFIABLE while withholding artifacts asks a reader to conclude something it
does not carry the inputs for. `bundle.trustLevel` recomputes and fails on a mismatch.

## Hostile archives

Nothing is extracted to disk, so traversal and symlink attacks are removed by construction rather than
by validation. On top of that: an allowlist of member names (not a denylist — a denylist must
anticipate every encoding of "go up a directory"), refused duplicates, a bounded read of one extra byte
so an understated declared size is caught during decompression, and a compression-ratio ceiling.

Six malicious names are parametrised, plus a decompression bomb and a truncated archive.

## `run_identity`, and why it is a table

The exporter needed the identities an outcome binds. They lived scattered across the sealed manifest,
the journey version, the runner profile and the fixture instance, and reconstructing them by joining
five tables at export time would produce a **current** answer for a run that finished months ago.

They are written once when the outcome is admitted and read verbatim afterwards, and the rows are
immutable by trigger: a run bound to a different build after the fact is a different run.

## Authorization is rechecked at generation

Not cached from the request. An export is asynchronous — request, work, download — and a membership
revoked in between must take effect. `test_a_revoked_membership_stops_an_export_at_generation` checks
authorization succeeds, revokes, and asserts generation now refuses.

Exporting is a separate permission from reading, because an export leaves the system; a VIEWER is
refused.

## Remaining real-evidence blockers

The acceptance gate asks for "a real baseline/candidate run and human assessment where available".
Neither exists:

- **No real run.** Every event in these bundles was constructed by a test, because modules 08 and 09
  are blocked. The bundle format, the integrity checks and the verifier are exercised adversarially;
  no bundle has ever carried a real screen-reader trace.
- **No human assessment.** Module 16 is implemented and nobody has used it, so `reviews.attribution`
  reports NOT_APPLICABLE — correctly: absence of a review is not a failed review.
- **No baseline/candidate comparison.** Module 15 does not exist yet; `Bundle.comparison` is defined
  and always `None`.

Synthetic bundles are useful conformance fixtures and do not replace the real export gate. **No bundle
has been uploaded anywhere**, and doing so would need separate approval.
