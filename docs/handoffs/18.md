## What a route handler is allowed to contain

Authority resolution, shape validation, one domain call, serialisation. No state transitions: every
one goes through the reducers, because a route that reimplemented a transition would be a second
definition of the lifecycle and the second one always drifts. The files are thin and repetitive, and
that is the trade — the repetition is plumbing, the decisions live in one place each.

## The cross-tenant existence oracle, and how it is closed

A 403 for a resource in another workspace confirms it exists. So:

- **No membership in this workspace → 404**, never 403. `test_a_member_of_another_workspace_gets_404_not_403`
  uses an outsider holding a *valid session and a real membership elsewhere*, who learns nothing.
- **A member lacking a permission → 403**, because the workspace's existence is not a secret from its
  own members.
- `problems.not_found()` is a single helper, so the two cases cannot drift into distinguishable
  messages. A parametrised test asserts the identical 404 across six resource families.

Every route's connection is **workspace-scoped at the database**, so a query that forgets its tenant
predicate returns nothing rather than another tenant's rows. A test creates a project in one
workspace and asserts it is absent from the other's listing.

## 202 means requested, not done

`POST /runs` returns 202 with `status: QUEUED` and `outcome: NOT_EVALUATED`. A 201 with something
outcome-shaped invites a caller to read a status as a verdict.

`status` and `outcome` are **separate fields and never merged**. A test asserts there is no `state`
key: a single merged field is how the distinction between "ended cleanly" and "established something"
gets lost, and that distinction is what the product rests on.

## Cancellation returns request metadata

```json
{"stopAcknowledged": false, "cancellationRequestedAt": "…", "meaning": "Cancellation is requested…"}
```

The test asserts `stopAcknowledged is False` and that the run is still non-terminal afterwards. A
`{"cancelled": true}` would be a lie told by a field name.

## If-Match, and why it is not optional

A revisioned mutation without `If-Match` is **428**, not applied to whatever state happens to be
current. A caller that did not read before writing made a decision about nothing.

A non-numeric validator (`W/"opaque"`) is refused rather than accepted and ignored — it cannot be
compared against a revision.

## Idempotency replays, and rechecks authority

The same key and body replay the first operation (`Idempotent-Replay: true`, one run not two). The
same key with a changed body is 409: two operations wearing one name, and replaying the first would
silently discard the second.

**The subtlety:** a replay returns the stored response only *after* this request's authority has been
resolved afresh. `test_a_replay_rechecks_authorization` revokes the membership between the original
call and the retry and asserts 404. A stored response returned without that check is a cached
authorization decision.

Without a key each call is its own operation. Idempotency is a client's tool for making a retry safe,
not a requirement the server imposes.

## Problem documents say little on purpose

`application/problem+json`, a closed `ProblemCode` a caller can branch on, and a `requestId` that is
the only identifier in the body. Every refusal goes through one exception handler, so no route can
answer with an exception's message — and the exception messages in this codebase deliberately carry
the specifics that help an operator, who is not an anonymous caller.

FastAPI's own validation errors are reshaped into the same document with the **count** of errors and
none of the messages. A validation error names the field and often echoes the value, and echoing a
value back is how a body that carried a token ends up in a response, a log and a bug report.

A test asserts no problem response contains `Traceback`, a file path, `psycopg`, a connection string,
the session token or the CSRF token.

## Unexpected fields are refused, not ignored

Every route declares its accepted field set. An ignored field is one a later version might start
reading, and a body that silently carried `workspaceId` would be one that eventually got believed.
A forged `workspaceId` is refused for the same reason, even though authority never comes from the
body.

## Enrollment tokens cannot be read back

A structural test walks the whole route table and asserts no path containing `enrollment-token`
exposes anything but `POST`. An endpoint that could reveal one would be a way to take over a tenant's
desktop, and "only administrators can call it" is weaker than "it does not exist".

## The contract is generated, not maintained

`scripts/generate_openapi.py` renders from the same `create_app` a request goes through, and CI runs
it with `--check`. A hand-written OpenAPI document describes what someone believed the API did.

## Unresolved API and runtime gaps

**No CLI and no generated clients.** The prompt asks for Python and TypeScript clients generated from
the contract plus a CLI for inspect, plan, run request, cancellation, export and offline verification.
`accessforge-verify` exists (module 17) and covers the last of those. The rest is **not done**, and
saying so is more useful than a generator run over a contract that is still missing nine route
families.

**The acceptance gate is not met.** It asks for a clean client to create a journey, request an
authorized local run, inspect its state and retrieve an export through the real API. Journey creation
has no write route because module 06 has no writer; an authorized run cannot execute because modules
08 and 09 are blocked. What a client *can* do through the real API today: create a project, request a
run, read its status and outcome, request cancellation and see it reported as requested rather than
done, enrol a runner and watch it refuse to be READY, list and read findings, submit a review, and
request an export.

That is real and it is less than the gate asks for. **BLOCKED, not substituted by a mocked server.**

**No external integration is published by this module**, and none was attempted.

## Addendum — standing grants and schedules (built after module 27)

Module 19 built the domain for execution grants and schedules; this module gave neither an HTTP
route, so a standing authorization could be created only by writing SQL. Ten routes close that:

| Route | |
|---|---|
| `POST,GET /execution-grants`, `GET /execution-grants/{id}` | Create and read. Every bound is required and finite — there is no NULL meaning unlimited on an authority that acts unattended. |
| `POST /execution-grants/{id}/revoke` | A revision, never a delete. Idempotent, because the operator most likely to revoke twice is the one unsure the first attempt landed. |
| `POST /execution-grants/{id}/revalidations` | **The door module 27 did not build.** See below. |
| `POST,GET /schedules`, `GET /schedules/{id}` | Bound to a grant at a specific revision. A schedule cannot name a journey the grant does not cover. |
| `GET /schedules/{id}/occurrences` | A skipped occurrence is a row with a reason, not an absence. |
| `POST /schedules/{id}/pause`, `/resume` | Paused, never deleted. |
| `POST /schedules/{id}/reapprove` | Re-bind to the grant as it now stands. |

Creating a grant requires `RUN_APPROVE`, not `RUN_REQUEST`. A grant is a machine that requests runs
unattended, and somebody trusted to request one run has not been trusted to build one of those.

### The defect this closes

Module 27's reconciliation sets `revalidation_required` on every grant a restore brings back — and
introduced **no way to clear it**. A restored grant was unusable forever. That is worse than a
missing control: the system looks like it is working, and the symptom is a schedule that quietly
stops firing with a skip reason nobody is reading.

### What building it found

Writing the test for the revalidation route exposed a second, subtler hole: **reconciliation did not
move the grant's revision**, so an operator holding a read from *before* the restore could confirm
the grant without re-reading it. "I have looked at this and it is still authorized" is the entire
content of a revalidation, and it was possible to supply it without looking. Reconciliation now
bumps the revision.

Fixing that surfaced a third: because a schedule is bound to the grant revision it was approved
against, and a restore now moves that revision twice, **every schedule stayed dead even after its
grant was confirmed**. `POST /schedules/{id}/reapprove` and migration 0016 are the way out.

The two confirmations are deliberately separate. "This standing authorization is still valid" and
"this recurring job should start running again" are different decisions, and a system that made the
second follow from the first would restart work nobody asked it to restart — overnight, against a
real desktop, on the strength of one click during an incident.
`test_a_restore_stops_a_schedule_and_only_two_deliberate_confirmations_restart_it` drives the whole
loop and asserts the schedule is *still* stopped after step one.

### What review then found

CodeRabbit raised 8 issues on this work; all 8 were real and all 8 are fixed.

| Finding | |
|---|---|
| **A bare string passed as a scope.** `[str(v) for v in value]` turns `"abc"` into three journey versions named after letters — accepted, stored, and discovered only when a schedule matches none of them | Arrays required; identifier entries validated before they reach a UUID comparison |
| **`timedelta.days` truncates**, so 365 days and 23 hours slipped past a 365-day ceiling | Compared in seconds. A bound that can be exceeded by rounding is not a bound. |
| **Check-then-use on the schedule revision.** The route validated `If-Match` and the persistence function took the row lock afterwards; a pause landing in that gap was accepted and then reversed by the re-approval's `paused_at = NULL` | The revision is confirmed inside the transaction while the row is locked, and `pause`, `resume` and `rebind_to_grant` all share one helper |
| **The contract documented a 422 the application never returns** — `RequestValidationError` is reshaped into an RFC7807 400. A client generated from it would branch on a field that never arrives | The generated document now carries a `ProblemDetail` schema with the real code enum, and the orphaned validation schemas are gone |
| **The contract declared no authentication at all**, so it read as an open API | `securitySchemes` for the session cookie and CSRF header, applied per operation; sign-in and health declare none |
| **A test annotated `-> dict` and returned an `httpx.Response`** | Corrected |
| **The cross-workspace 404 test used a random UUID**, which proves only that an unknown id is a 404 | It now creates a real grant in a second workspace and asserts it is invisible — from the read route *and* the listing |

The revision fix is the one worth remembering: it is the same class as the check-then-use the
idempotency layer was designed around, reintroduced one layer up because the check moved into the
route and the lock stayed in persistence.

**The fixes were not themselves independently reviewed** — CodeRabbit was rate-limited on the
second pass. The revision fix in particular is a concurrency change, which is the category where my
own review is worth least.

## Addendum — the live event stream, the generated clients and the CLI

### The event stream

`GET /events/stream` (SSE) and `GET /events/snapshot`. Module 19 built `events.py` — including
`as_sse()` and `ReplayGap` — and nothing ever served it.

Four properties, each of which fails silently when missing: a cursor below the retention floor
produces a **reset** naming the snapshot, not a short stream; the cursor is an outbox row id and a
timestamp-shaped `Last-Event-ID` is refused; authority is rechecked on **every poll**, not once at
connection time; and nothing the stream says can be read as "the run finished".

**Three defects found while building it, all by tests:**

1. **The producer was a plain generator.** Starlette iterates those in a worker thread, where
   `time.sleep` cannot be interrupted — so a client closing its tab left a thread polling the
   database for the stream's whole remaining lifetime. A test that read one event and closed hung
   for five minutes.
2. **`import anyio` does not give you `anyio.to_thread`.** The failure mode was the worst available:
   the response had already begun with a 200, so the client saw a successful *empty* stream and the
   error went to a log nobody reads.
3. **The request-scoped connection was held for the stream's lifetime.** FastAPI closes a generator
   dependency after the response completes — minutes later for a stream — leaving one "idle in
   transaction" row per subscriber, blocking vacuum on every table it touched.

The tests run against a **real uvicorn process**, because Starlette's `TestClient` buffers a
streaming response in full before returning any of it. Measured, not assumed: a five-event generator
sleeping two seconds between events yielded nothing for ten seconds and then everything at once.

### Readable operation ids

FastAPI's default builds an operation id from the *path*, producing
`revalidate_execution_grant_v1_workspaces__workspace_id__execution_grants__grant_id__revalidations_post`
— which a generated client uses as a method name, and which changes whenever the path changes, so
moving a route silently breaks every consumer keyed on it. Operations are now named after their
handler, and a collision raises at startup rather than producing two operations sharing an id (where
the second overwrites the first in a client's table and the route becomes uncallable while working
perfectly in a browser).

### The clients

| | |
|---|---|
| Generated | The operation table — method, path, parameters, whether it mutates. Python and TypeScript, from `contracts/openapi.json`, which comes from the live app. CI runs `--check`. |
| Not generated | **The transport.** Cookies, CSRF, `If-Match`, `Idempotency-Key` and what a problem document means are decisions a contract does not describe; generating them would produce a confident client that gets them wrong. |
| Not generated | **Response types.** Every route returns `dict[str, Any]`, so a type-generating client would emit `Any` everywhere and imply a precision that does not exist. |

`Requested` is the whole answer to a 202 — no truthiness anybody would misread, no field a caller
could mistake for a verdict. The CLI prints `"state": "requested"`, so `jq -r .outcome` returns
nothing useful, which is correct.

The generator emits **ruff-formatted** output, because otherwise the file is generated one way and
formatted another and `--check` fails on a tree nobody edited.

A client bug worth recording: it first read the CSRF token from the sign-in body. The API
deliberately never puts it there — a body copy reaches the console, the network panel of a shared
screen, and any log that records a response — so the client read a cookie instead, and now refuses
to store a session when either cookie is absent rather than looking signed in and failing every
write one request later.

### The TypeScript side

The web client stays hand-written: its discriminated result union and session-epoch handling are
decisions a generator cannot make. The cost is drift, and a type checker cannot see a path — so
`apps/web/src/api/contractCoverage.test.ts` asserts every URL it builds is one the contract declares,
with a guard against the matcher silently extracting nothing. It also **lists the routes the API
serves that no screen uses yet**, so a missing screen is visible rather than assumed absent.

### Still not built

`/builds`, `/patches`, `/verifications`, `/integrations/github`, `/publications`,
`/webhooks/github`, and `/runners/{id}/preflights`. The patch and publication families belong to
modules 14, 15 and 20, which do not exist; builds and preflights have domain support and are simply
not done.

**A gap this work exposed rather than closed:** `POST /runs` accepts a `manifestDigest` and does not
check that a manifest with that digest was ever sealed. Module 22's UI refuses to request a run when
nothing is sealed — a check in the one place a determined caller can skip. Recorded here rather than
hidden behind a test fixture that seals something to look thorough.

**45 `/v1` paths.** Verified live against real PostgreSQL, not only through the test client.
