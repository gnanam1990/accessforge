# Handoff 16 — Human review

- **Module:** 16
- **Requirements:** FR-011, FR-012. **Invariants:** INV-11, INV-12, INV-16

## The three statements the prompt asks for, separately

The handoff is required to say independently whether the workflow is implemented, whether a human
review occurred, and whether a reviewer tested the product with assistive technology. Those are three
different claims and collapsing them is how a process gets credited for participation it never had.

| Claim | Answer |
|---|---|
| **Is the workflow implemented?** | **Yes.** Review requests, submissions, three verdicts, independence policy, staleness binding, append-only corrections, finding lifecycle, separate attribution. 30 integration tests against real PostgreSQL. |
| **Did a human review occur?** | **No.** No person has used this. Every review in the test suite was written by the test, with fabricated reviewer ids. |
| **Did a reviewer test the product with assistive technology?** | **No.** Nobody has, and nobody could: module 08 is blocked, so the product cannot drive a screen reader at all. |

Missing human participation stays an explicit release-proof blocker.

## What a review is prevented from becoming

**A verdict about the run.** `test_a_review_cannot_change_the_run_outcome` reads the run's status,
outcome and revision before and after an ACCEPT and asserts they are identical. A structural check
would be weaker — the point is not that no column here is named `outcome`, but that recording an
acceptance leaves what the evidence established untouched (INV-12).

**An execution authority.** ACCEPT is not RUN_EFFECTS, PATCH_APPLY, GITHUB_PUBLISH or a deployment
approval. The test reads module 03's permission matrix rather than restating the rule: a second copy
would be a second thing to keep in agreement, and the two would eventually disagree. `REVIEWER_ROLES`
is *derived* from the same matrix for the same reason.

**A claim about participation.** A request and a submission are separate tables. Assignment
establishes that someone was asked, and `requested_of` is nullable and explicitly documented as a
preference rather than a lock — never as evidence that the named person did anything.

## Staleness is checked against a second source

`submit_review` takes both what the reviewer looked at and what the system holds now. Two parameters,
because comparing a stored record to itself always agrees — a single-source check would pass
unconditionally while looking like protection. A structural test asserts both parameters exist.

Carrying an acceptance forward onto changed bytes would attribute to a reviewer an opinion about
content they never saw.

## Independence is enforced on canonical identity

On `reviewer_id`, the actor id. A display name, a second session or an alias all resolve to the same
value. Enforced on anything a person controls, the policy would be a suggestion.

## Append-only, with the history intact

Reviews are immutable by database trigger — `UPDATE` and `DELETE` both raise. A correction is a new
review pointing at the one it supersedes, and `review_history` returns **both**. Showing only the
latest would present a changed mind as a first impression.

`effective_reviews` filters to what is in force; the history function does not.

## There is nowhere to record demographic or disability data

Not an unused nullable column, not a JSONB blob that could hold one. A test reads
`information_schema` and asserts no column name contains `disability`, `impairment`, `demographic`,
`age`, `gender` or `ethnicity`, and that there is no `metadata` or `extra` free-form field either.
A field that exists gets filled.

**Assistive-technology use is recorded and never inferred.** `used_assistive_technology` is set only
when the reviewer says so — not from their role, not from workspace membership, not from the fact
that a review exists. "A person accepted this" and "a person accepted this having driven it with a
screen reader" are different claims, and the release proof asks the second.

## The finding lifecycle

`REPRODUCED` cannot be opened from a run whose outcome is not FAIL. That is easy to get wrong,
because an inconclusive run frequently *contains* a real-looking failure — and a confirmed defect
asserted on evidence that established nothing is the harm INV-02 exists to prevent.

`RESOLVED` requires a review, and the review must be an ACCEPT. Both are checked: a resolved finding
with no review attached is indistinguishable from one nobody looked at, and citing a
CHANGES_REQUESTED review resolves nothing.

Dismissal and reopening are available to a reviewer, both require a reason, and both are recorded
with the actor. A dismissal is a judgement about a finding, not a deletion of it.

## Separate attribution in every serialized view

`serialize_for_display` returns `machineOutcome` and `humanAssessments` as two top-level keys, each
carrying an `establishedBy` line — "deterministic evaluation of recorded evidence" against "a
person's judgement, attributable to them". A view that flattened them would let a reviewer's ACCEPT
read as the system having verified something.

## Mutation checks

| Mutation | Result |
|---|---|
| Stale patch digest accepted | 1 test fails |
| Self-review allowed | 2 tests fail |
| RESOLVED without a review | 1 test fails |
| RESOLVED citing a non-ACCEPT review | 1 test fails |
| REPRODUCED openable from an inconclusive run | 1 test fails |
| The immutability trigger is not created | 1 test fails |

The last one was invalid on the first attempt: renaming the trigger still creates a trigger, so it
still fired and nothing failed. Re-run with the `CREATE TRIGGER` removed entirely, it failed the
immutability test. A mutant that does not change behaviour proves nothing.

## A constraint that caught the test helper

The first version of `_finished_run` set `run.outcome` with an `UPDATE`. The `run` table holds a
check constraint pairing status with outcome, and a QUEUED run with a FAIL outcome is a state the
schema refuses. The helper now drives the run through the reducers, which is what any real caller
does.
