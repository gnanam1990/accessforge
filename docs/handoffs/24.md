## What exists now

Every route in the UI-UX map now has a screen. Three were added here — reviews, exports and the
repair workspace — plus two read routes, `GET /review-requests` and `GET /reviews/{id}`, and an
export control on the run screen.

The module's objective is that **patch application, machine verification, human acceptance and
external publication not be compressed into one ambiguous Approve button.** Three of those four do
not exist in this build, and the honest way to keep them uncompressed turned out to be to say so.

## The four boundaries

**Being asked is not reviewing.** The queue shows how many assessments each request has received,
and zero is displayed as zero. Treating an assignment as a review is how a process reports completed
review that never happened.

**A review is bound to exact material, and the server checks the binding.** The form sends both the
digests the reviewer looked at *and* the digests the request holds now. That looks redundant and is
not: comparing a record to itself always agrees, so a form that read one value and sent it twice
would make the staleness check pass unconditionally while appearing to protect something. A mutation
that sends one digest twice is killed by a test.

**Assistive-technology use is asked, never inferred.** A required choice with no default, because "a
person accepted this" and "a person accepted this having driven it with a screen reader" are
different claims. Choosing "no" clears the detail field, because the server refuses detail from
someone who reported using none — one of the two would be wrong and the record must not guess which.

**A review authorizes nothing.** The limits come from the server with the record, so this interface
cannot compose a shorter list — and the shortest version is the one that makes an `ACCEPT` look like
a release decision. A mutation that trims the server's list is killed.

**Nothing asks who the reviewer is.** No demographic question, no disability question, no study
participation. Whether they used assistive technology is a fact about *this review*; a test asserts
the screen contains no question of the other kind.

## The export screen

The limitations are rendered **above** the instructions for using the bundle, and a test asserts the
heading order — an export is the artefact most likely to be read by somebody who was not present,
and the failure mode is a bundle that reads as proof of accessibility.

Trust level is displayed as attribution, not validity, in the exporter's own vocabulary
(`FULLY_VERIFIABLE`, `LIMITED_DISCLOSURE`, `INCOMPLETE`). The first version of that map guessed two
level names that do not exist; a real bundle came back `INCOMPLETE` and fell through to the
unrecognised branch. The fallback behaved correctly — which is the only reason the mistake was
visible — and both behaviours now have tests.

Retention is labelled a snapshot of export time. Nothing is published, there is no share link, and
the screen says publication is a separately authorized `GITHUB_PUBLISH` workflow belonging to module
20, which does not exist.

## The repair workspace, and why it is a statement

Modules 14 and 15 do not exist: no patch table, no verification table, no route for either. This
screen shows no diff, no comparison and **no approval control of any kind**. It lists what each
missing piece would have to establish before an approval could honestly appear — the diff and its
base, the reproduced finding, the isolated build, the matched comparison, the protected checks, and
the `PATCH_APPLY` scope rechecked at application rather than when the button was drawn.

An inert diff viewer beside a disabled Approve button would look identical to one waiting for data,
and somebody would eventually wire it to something. There is nothing here to wire, and a test
asserts no control matching `/approve/i` exists on the page.

## A latent failure this module tripped over

`test_the_most_recent_preflight_is_the_one_that_counts`, from module 07, inserted a failing
preflight at a hard-coded `2026-09-10T12:01:00Z` while the successful one took the column's `now()`
default. It asserted the right thing only while the wall clock was before 12:01 UTC on that date.
It passed at 09:30 UTC during module 23's verification and failed at 12:08 UTC during module 24's —
and would have failed on `main` from then on. The timestamp is now derived from the row it must
supersede, so the test says "later than the one already recorded" rather than naming a moment.

Fixing a merged module's test from here is a judgement call. It was breaking `main`, the cause had
nothing to do with the code under test, and leaving it would have meant every later module inheriting
a red suite.

## No independent review, and what I did instead

CodeRabbit reported **rate limited** on this pull request, so module 24 is the first in this
sequence with no independent review. Rather than merge on my own say-so, I re-read the diff against
the specific defect classes the previous three reviews found, and four of them were present:

| Found by re-reading | Why it mattered |
|---|---|
| The review queue took one page with no cursor and no truncation indicator | The same shape a review found in module 22's environment listing, written again from memory a day later. A prefix presented as the queue leaves a request nobody can see still waiting for somebody |
| The client rendered that one page as the whole queue | The same finding on the client side; it now follows the cursor and says so when it stops early |
| The queue cursor reached PostgreSQL unvalidated | A malformed value is an unhandled driver error and a 500, on a query-string parameter |
| `/reviews/new` fetched a review called "new" | A request the server can only refuse, putting a 400 in the log for a page working correctly |

All four are fixed, each with a test, and four mutations confirm the tests fail without them. That
is not equivalent to an independent review — I found the classes I already knew to look for, which
is exactly the limitation that makes independent review worth having — and this module should be
re-reviewed when the rate limit clears.

## What is not proved

**No review has been submitted through the interface against real material**, because no review
request can exist: a request binds a patch digest and a verification digest, and nothing produces
either. The form is exercised against the real route in the integration tests — staleness, self-
review, the assistive-technology requirement, the unable-to-assess rule, and the permission boundary
all refuse correctly — but the digests in those tests are constructed by the test, not by a patch
sandbox.

**No route creates a review request, deliberately.** Building one would mean accepting patch and
verification digests invented by its caller.

**The acceptance gate is partly met.** An authorized person can obtain a private export of real
evidence and read exactly what it does and does not establish. They cannot inspect a real candidate,
because none can exist. The UI cannot turn an `INCONCLUSIVE` repair into `VERIFIED` — there is no
control that could — and it does not treat absent human participation as completed review, which the
queue's zero-count and its test establish.

**No actual screen reader, and no automated accessibility scan** — the same position as modules 21,
22 and 23, for the same reasons. The keyboard flows were driven by `userEvent` in the unit tests and
programmatically in the live browser.

**The diff viewer does not exist.** Task 2 asks for an accessible unified diff with a plain-text
alternative and file navigation. There is no diff to render, and a diff component with no diff is
the kind of thing that gets wired to something later. It belongs with module 14.
