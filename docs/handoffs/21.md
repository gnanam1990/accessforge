# Handoff 21 — Accessible application shell and design system

- **Module:** 21. **Requirements:** FR-014, FR-016, FR-019
- **Invariants:** INV-07, INV-12
- **Owned paths:** `apps/web/`, `apps/api/src/accessforge_api/routes/session.py`,
  `tests/integration/test_session_routes.py`

## What exists now

`apps/web` was a single file whose only job was to give the TypeScript workspace a build target. It
is now a React 19 + Vite application with the route map from UI-UX §3, the design tokens from §2,
the shared primitives §2 asks for before any screen is composed, and the operational states §7
requires every route to implement.

The **screens** belong to modules 22–24. Every route renders its real heading, breadcrumb and focus
behaviour, followed by an explicit statement of which module owns the screen and that nothing on the
page is data. That is deliberate: the acceptance gate forbids presenting a placeholder route as a
completed feature, and an empty state would be its own lie — it would claim the server had been
asked and had answered.

## The session routes, and the thing this module refused to invent

The shell needs to know who is signed in and which workspaces they may enter. No route provided
that, so this module added three:

| Route | Behaviour |
|---|---|
| `POST /v1/sessions` | Exchange an identity-provider assertion for a browser session |
| `GET /v1/session` | The principal and their **live** memberships |
| `DELETE /v1/session` | Revoke the session server-side and clear both cookies |

**There is no password, and no credential store was invented.** `issue_session` has existed since
module 03 and deliberately does not authenticate anyone; establishing identity belongs to a
configured provider. `ACCESSFORGE_IDENTITY_PROVIDER` defaults to `none`, and with that setting
`POST /v1/sessions` answers **503 `DEPENDENCY_UNAVAILABLE`**, naming the missing configuration. The
UI renders that as a dependency failure with no sign-in form at all, rather than a login box that
could never succeed and would make the person conclude their credentials were wrong.

One provider is implemented and it is honestly labelled: `local-development` accepts an email with
**no secret**. That is an authentication bypass by construction, so:

- it is off unless the variable is set explicitly;
- `ApiSettings` **refuses to start** with it in any environment other than `local` — setting the
  variable is not sufficient;
- while off, the route never reveals whether an account exists;
- while on, an unknown account and a disabled account get byte-identical refusals, so the easiest
  route in the product to enumerate users does not enumerate them.

Two cookies. The session cookie is `HttpOnly` — script must not read a credential. The CSRF cookie
deliberately is not: the browser echoes it into a header the server compares against a stored hash,
and a cross-site request can send the cookie without being able to read it. Neither token is
repeated in a response body, and a test asserts that.

## What the client does with each answer

`ApiClient.request` returns a discriminated union — `ok`, `accepted`, `cancelled`, `offline`,
`unauthenticated`, `stale`, `problem` — and **not** `T | null`. `null` is what a caller renders as
"nothing here yet", and "nothing here yet" is the wrong thing to show someone whose request was
refused. The prompt states it directly: a failed request must not become an empty result.

- **202 is `accepted`, never `ok`.** A caller treating every 2xx alike reports a queued run as a
  finished one.
- **Nothing is retried.** Not a mutation — a retried approval is a second approval — and not a read
  either, because whether the answer is still wanted is the caller's question.
- **Every request carries a session epoch.** It advances on sign-out, on a 401 anywhere, and on a
  workspace switch. A response whose epoch is stale resolves as `stale` and is discarded. The
  responses still arrive; what changes is that none of them can be painted into the screen of the
  next tenant or the signed-out shell.
- **Offline is distinguished from a server refusal**, because they ask the reader to do different
  things and "check your connection" is useless advice when the server is down.
- `credentials: 'same-origin'` and `redirect: 'error'`. `include` would send the session cookie
  cross-origin; a followed redirect would send it wherever the redirect pointed.

## Accessibility decisions that are load-bearing

**Focus after a route change** moves once, to the new `<h1>`, and never on first paint or on a
query-string-only change. Whether this is the first paint is recorded **once for the application**,
in a provider above every route — see the defect below for why that sentence is the whole point.

**The skip link** is rendered always, moved off-screen with `transform` (never `display: none`,
which would remove it from the tab order) and moves focus into `<main>` **explicitly**.

**One live region**, polite, bounded to three pending messages and deduplicated against the last
one. A live region fed from a run's event stream reads every event, and a reader then cannot hear
anything else — including the control they are trying to operate. Announcing never moves focus.

**Form failure** moves focus once to a focusable error summary linking to each affected control,
keeps the specific inline error connected by `aria-describedby`, preserves the entered value, and
re-announces on an identical repeat failure. Nothing validates on blur.

**Status is text plus a shape**, never colour. There is no mapping that produces a success
appearance from a status: a green `COMPLETED` would be the UI deriving a verdict, and `COMPLETED`
says only that a run ended.

**Contrast is measured, not asserted.** `src/styles/styles.test.ts` parses `tokens.css` and computes
WCAG relative luminance from the declarations themselves — 4.5:1 for 24 text pairs and 3:1 for 6
focus and control-boundary pairs, in both palettes. A ratio table in a document is true at the
moment somebody measured it; this fails the build the day a hex value is nudged. It found one real
problem: `--af-border-strong` was `#94a3b8`, which is **2.45:1** against the light background, so
every input and secondary button had a boundary below the non-text minimum. It is now `#6b7f99`
(3.92:1) and `#7c8ca3` in dark (4.28:1). `--af-border` stays decorative and is documented as such,
with a structural test asserting that no control is bounded by it.

The same file asserts the rules that a future edit could break invisibly: `outline: none` appears
nowhere, the ring is 3px with an offset, reduced motion zeroes the duration token *and* neutralises
transitions declared elsewhere, controls have a 44px `min-height` rather than a fixed height, no
`pt`/`dp` units appear in CSS, and the root font size is not pixel-pinned.

## The custom keyboard pattern

One: `Tabs`, following the ARIA Authoring Practices tab pattern — only the selected tab in the tab
order, Left/Right/Home/End with wrapping, automatic activation because the panels are already
loaded, and each panel labelled by its tab. Everything else in the foundation is a native element:
`<button>`, `<a>`, `<label>` + control, `<table>`, `<dialog>`, `<details>`, `<select>`, `<fieldset>`.

## Three defects a real browser found and the unit tests did not

These were all found by driving the built application against the live API, and each one is now
covered by a test that fails without the fix.

**1. Route focus was tracked per component instance.** The record of "have we navigated yet" lived
in a `useRef` inside `RouteHeading`. React reuses the component instance when a navigation stays
within the same route element, so heading-to-heading moves worked and every unit test passed. A
navigation that swaps the subtree — the workspace chooser to a workspace — mounts a *fresh*
`RouteHeading` whose ref is empty, which the component read as "first paint" and declined to move
focus. The single most likely keyboard navigation in the product silently did nothing. The record
now lives in `RouteFocusProvider`.

**2. The skip link did not move focus.** With a plain `href="#af-main-content"`, activating it in a
real browser left focus on the link, so the next Tab went straight back into the header. The unit
test asserted the target was *focusable*, which it was. It now asserts focus is *in* main, and the
component moves it.

**3. Sign-out cleared only one of its two cookies.** The handler built a new response from
`dict(response.headers)`, and a dict keeps one value per name — so one of the two `Set-Cookie`
deletions vanished and the browser kept a cookie the server believed it had cleared. Every status
assertion passed. The test now counts the headers and checks each carries a past expiry.

A fourth was found by vitest rather than the browser: an explicit `scrollIntoView()` after `focus()`
threw in jsdom as an uncaught exception while the test still passed. `focus()` already scrolls; the
call was removed rather than stubbed.

### Against the real API, in a real browser

Vite dev server proxying `/v1` to `python -m accessforge_api` with
`ACCESSFORGE_IDENTITY_PROVIDER=local-development`, against the local PostgreSQL with two seeded
workspaces and one member. Observed:

- Sign-in with an empty field: focus moved once to the error summary; no request was sent.
- Sign-in with the seeded address: `201`, `HttpOnly` session cookie and readable CSRF cookie set,
  neither token in the body; the shell then listed **Alder Staging (owner)** and **Zebra Local
  (viewer)** — the real memberships, from the real database.
- Activating the skip link: focus landed on `#af-main-content`.
- Following a navigation link: focus landed on the new `<h1>`; the URL is a real deep link.
- Deep link to a workspace with no membership: "Not available", with no mention of permission,
  membership or another tenant.
- Theme: default sets no `data-theme` and follows the system; choosing Light set the attribute and
  persisted it; the page re-rendered in the light palette.
- 320 CSS pixels: no horizontal overflow, navigation collapsed to a labelled "Menu" disclosure,
  every action still present. 640×400 (200% of 1280): no horizontal overflow, sign-out reachable.
- Sign-out: both cookies cleared, no tenant name or address left in the document, sign-in shown.

Ten mutations, each run against the tests that should notice, each restore verified byte-identical
by SHA-256.

| Mutation | Result |
|---|---|
| The request epoch stops discarding a response that outlived its session | 3 tests fail |
| A non-member workspace answered with a permission message instead of not-found | 2 tests fail |
| Route focus tracked per heading instance again | 1 test fails |

| The error summary no longer re-announces an identical repeat failure | 1 test fails |
| Every tab left in the tab order | 1 test fails |

Two of the ten had to be rewritten: the first attempt at each changed a line the tests never
execute, so the mutant "survived" without saying anything about the guard. That is recorded because
a surviving mutant is only evidence when the mutation actually reached the behaviour.

## What is not proved

**No actual screen reader was used.** The prompt asks for the navigation and form flow to be run
through the supported VoiceOver profile. VoiceOver remains unconfigured on this host
(`docs/capabilities.md` §5.1, BLOCKED), so this module's accessibility evidence is: semantics
asserted through the accessibility tree in unit tests, keyboard operation driven in a real browser,
and measured contrast. **That is not the same as a reader having read it**, and the difference is
exactly the one this product exists to insist on. The untested matrix is every reader and every
platform: VoiceOver on macOS, NVDA and JAWS on Windows, Orca, TalkBack, VoiceOver on iOS.

**No automated accessibility scan is included.** Adding one would be easy and would report a clean
result on all of the defects above — none of the three is detectable by a static rule. The prompt
is explicit that scans and screenshots are complementary rather than sufficient; a green scan
alongside three unverifiable claims would have been worse than no scan.

**Focus behaviour inside the modal is the platform's, not this code's.** `Dialog` uses
`showModal()`, which supplies the focus trap, inertness and backdrop. jsdom implements neither
`showModal` nor `close`, so the component degrades to opening by attribute there and the tests
verify the return-focus and single-close-path behaviour only. The trap itself is unverified by this
suite.

**The acceptance gate is partly met.** A fresh operator *can* sign in through the implemented mode,
choose an authorized workspace, navigate between sections with the keyboard, and recover from a
denied deep link, an ended session and an unreachable server. They cannot do any of it through a
screen reader that anyone has watched, and the "implemented mode" is a development bridge rather
than a deployable identity provider. Both are stated rather than smoothed over.

**No screenshots are committed.** The observations above were made against a running stack; the
repository's evidence policy keeps run artefacts out of version control (`.evidence/`, gitignored),
and a committed PNG would be a claim nobody could re-derive.

## Running it

```
ACCESSFORGE_IDENTITY_PROVIDER=local-development uv run python -m accessforge_api
pnpm --filter @accessforge/web dev
```

The dev server proxies `/v1` to `http://127.0.0.1:8080` on the same origin, so the `SameSite=Lax`
cookies behave exactly as they do in a deployment. Cross-origin development would need
`SameSite=None`, which is the setting that makes a cookie available to a cross-site request.
