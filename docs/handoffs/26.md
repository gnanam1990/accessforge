## What exists now

A workspace has a configured allowance, its consumption is measured, requesting a run is charged
against it, and the last unbuilt route in the UI map — settings — is a screen. There is a
source-bound threat model and an adversarial probe suite that attacks every read route from where an
attacker actually stands.

## A limit that is a limit

`admit_within_budget` locks the entitlement row before it reads usage, compares, and records — all
in the transaction that creates the run. Without the lock two requests arriving together both read
the same total, both find room, and both are admitted; the workspace ends up over by exactly the
number that raced, and no single line of code is wrong.

`test_concurrent_admissions_cannot_overspend_the_limit` fires **eight requests on eight connections
against a limit of three** and asserts exactly three are admitted and the recorded total is three.
A mutation that drops `FOR UPDATE` fails it. That test is the module.

Live, through the real API: five runs admitted against an allowance of five, the sixth refused with
`429 QUOTA_EXHAUSTED`, `kind: RUN_ADMITTED`, `limit: 5`, `used: 5`. "Quota exceeded" alone tells an
operator nothing about what to change.

## The decisions worth reading

**A workspace with no entitlement is refused, not treated as unlimited.** "Nobody has decided what
your allowance is" and "you may do anything" are different states, and a generous default makes them
the same one. This has an operational cost, stated below.

**Usage events are idempotent by `(workspace_id, event_key)`.** At-least-once is the only delivery
this system has; a metering table without a natural key double-counts under redelivery. A run
request's idempotency key *is* its usage event key, so a retry replays rather than being refused for
exhausting a limit its own first attempt consumed.

**Measured, estimated and unavailable are three numbers.** A provider reporting its own token count
is `ESTIMATED` and still counts against the limit — excluding it would leave anything self-reported
unbounded. `UNAVAILABLE` is a *count of events*, never a quantity, because a quantity of zero reads
as nothing having happened.

**No price, no currency, no payment instrument, no computed saving.** Asserted structurally against
the schema's column names and against the response's field names — not against its prose, because
the response says in words that nothing here is a cost and a text search would flag that sentence
while missing a field called `spend`.

**Entitlements and retention policies are revisioned appends requiring the revision the caller last
read.** An entitlement that changed in place would make every past admission unexplainable: the row
would say what is permitted now and nothing would say what was permitted then.

**Retention is seven classes, not one number.** A single "keep evidence for N days" makes a decision
about speech recordings by way of a decision about diagnostics. Each class declares whether deleting
under it invalidates a completeness claim, and **that flag is not configurable** — it comes from
what the class is. An administrator setting it to false would not make deletion stop breaking
anything.

**A partial retention revision is refused.** It would leave unlisted classes at whatever the last
revision said, and a reader could not tell a decision from a leftover.

## The probe suite

`test_boundary_probes.py` signs in as a real member of workspace A and attacks workspace B, which
holds real records — a project, a run, an attempt with an admitted reader observation, and 99,999
metered tokens. Probing a nonexistent id proves only that nothing is nothing.

The central test collects **all twenty read routes** and asserts every one answers `404
RESOURCE_NOT_FOUND` and nothing else. A route answering 403, or a different code, or a longer
message, confirms the workspace exists and that something is in it. Collected into one test on
purpose: a route added without the shared refusal shows up as a diff on a list rather than as a
test nobody wrote.

The rest: the refusal body carries none of the other workspace's content; a forged `workspaceId` in
a body is refused rather than ignored; **my run plus their attempt** is refused (both identifiers
are individually legitimate, and a route validating each separately would answer); another
workspace's usage is not charged to mine; revoked membership and revoked sessions stop working on
the *next request*; and a canary sweep over 25 paths finds no session token, CSRF token, traceback,
`psycopg` string or filesystem path in any response.

## No independent review, and what I did instead

CodeRabbit reported **rate limited** on this pull request, as it did on module 24. I re-read the
diff against the defect classes the earlier reviews found, and three things were wrong:

**The concurrency limit was stored, displayed and never checked.** `max_concurrent_runs` had a
column, a value in the settings screen and no enforcement anywhere — precisely the dead guard this
codebase argues against. It is now checked inside the same locked transaction as the daily
allowance, *before* it, because it is the cheaper refusal and the one that resolves without anybody
doing anything. It raises its own exception with its own sentence: a daily limit is raised by an
administrator, and reporting this as "quota exhausted" would send an operator to change a number
that is not the problem.

**The usage event key was not namespaced by route.** A caller chooses their own idempotency key. A
key already used for some other operation would have read as a retry of this admission, and the run
would have been created without being charged. The key is now `POST /runs:<key>`.

**The settings screen holds a copy of the permission matrix.** `WORKSPACE_CONFIGURE` is owner-only,
and the copy is right — but a copy is a copy. There is now a test pinning it for `MAINTAINER`, the
role most likely to be added by mistake, since the server refuses either way and the visible cost of
being wrong is showing somebody a form whose submission always fails.

Four mutations confirm the three fixes and the role copy. This is not equivalent to an independent
review: I found the classes I already knew to look for.

## The operational consequence you should know about

**Every existing workspace now needs an entitlement before it can request a run.** A workspace
created before migration 0013 has none, and `POST /runs` answers `503 DEPENDENCY_UNAVAILABLE`
naming the missing configuration. That is deliberate and it is a breaking change: the alternative is
a default allowance, and a default allowance is a limit nobody chose. Module 18's test fixture was
updated to configure one, with a comment saying why.

## What is not done

The prompt's ten tasks are not ten deliverables of equal size, and six of them have no backend to
attach to.

- **Only run admission and concurrency are charged.** Actions, wall-clock seconds and model tokens
  have limits, columns, reporting and enforcement, and nothing records them — because nothing
  dispatches an action or calls a model. Those three limits are *enforceable and unenforced*, which
  is a different statement from enforced.
- **No scoped deletion route.** Module 10 can redact and delete an artifact and finalization counts
  a deleted required artifact as missing; there is no route that deletes across primary records,
  derived views, caches and export storage, and no test of restoring a backup that predates a
  deletion.
- **No structured telemetry beyond `metrics.queue_health`.** No counters for reader or preflight
  failure, model failure, budget rejection or export integrity.
- **No rate limiting.** An authenticated member can issue unlimited requests to any read route. The
  budget bounds *work*, not requests.
- **No `ExecutionGrant` settings, no GitHub payload approval.** Grants are module 19's schema with
  no route; publication is module 20 and does not exist.
- **No dependency vulnerability scanning.** CI pins lockfiles and scans for committed secrets; there
  is no SCA tool.
- **No build-worker egress probe**, because there is no build worker. The claim that a build cannot
  reach the control plane or a metadata service is untested in both directions.
- **No privilege-revocation drill against a deployment**, because there is no deployment.
- **No external penetration test and no legal advice.** Every probe here was written by the person
  who wrote the code it probes, which is the weakest form of adversarial review there is. The threat
  model says so in its own section rather than in a footnote.

**The acceptance gate is partly met.** The declared deployment mode's tenant, authority, evidence
and budget boundaries withstand concrete probes through the real HTTP surface, and quota behaviour
is observable through the real service. The desktop boundary is not probed at all — it is one
dedicated local machine and a procedural agreement, and nothing prevents an operator enrolling the
computer they are sitting at. No bypass capable of granting unauthorized execution or a false PASS
was found; nothing was found because nothing executes.

**No actual screen reader** exercised the settings screen. Keyboard flows were driven by `userEvent`
in the unit tests and programmatically in the live browser — the same position as modules 21–24.
