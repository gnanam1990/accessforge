## What exists now

A workspace has a configured allowance, its consumption is measured, requesting a run is charged
against it, and the last unbuilt route in the UI map — settings — is a screen. There is a
source-bound threat model and an adversarial probe suite that attacks every read route from where an
attacker actually stands.

## A limit that is a limit

`admit_within_budget` locks the entitlement row before it reads usage, compares, and records — all
in the transaction that creates the run. Without the lock two requests arriving together both read
the same total, both find room, and both are admitted; the workspace ends up over by exactly the
number that raced, and no single line of code is wrong.

`test_concurrent_admissions_cannot_overspend_the_limit` fires **eight requests on eight connections
against a limit of three** and asserts exactly three are admitted and the recorded total is three.
A mutation that drops `FOR UPDATE` fails it. That test is the module.

Live, through the real API: five runs admitted against an allowance of five, the sixth refused with
`429 QUOTA_EXHAUSTED`, `kind: RUN_ADMITTED`, `limit: 5`, `used: 5`. "Quota exceeded" alone tells an
operator nothing about what to change.

## The decisions worth reading

**A workspace with no entitlement is refused, not treated as unlimited.** "Nobody has decided what
your allowance is" and "you may do anything" are different states, and a generous default makes them
the same one. This has an operational cost, stated below.

**Usage events are idempotent by `(workspace_id, event_key)`.** At-least-once is the only delivery
this system has; a metering table without a natural key double-counts under redelivery. A run
request's idempotency key *is* its usage event key, so a retry replays rather than being refused for
exhausting a limit its own first attempt consumed.

**Measured, estimated and unavailable are three numbers.** A provider reporting its own token count
is `ESTIMATED` and still counts against the limit — excluding it would leave anything self-reported
unbounded. `UNAVAILABLE` is a *count of events*, never a quantity, because a quantity of zero reads
as nothing having happened.

**No price, no currency, no payment instrument, no computed saving.** Asserted structurally against
the schema's column names and against the response's field names — not against its prose, because
the response says in words that nothing here is a cost and a text search would flag that sentence
while missing a field called `spend`.

**Entitlements and retention policies are revisioned appends requiring the revision the caller last
read.** An entitlement that changed in place would make every past admission unexplainable: the row
would say what is permitted now and nothing would say what was permitted then.

**Retention is seven classes, not one number.** A single "keep evidence for N days" makes a decision
about speech recordings by way of a decision about diagnostics. Each class declares whether deleting
under it invalidates a completeness claim, and **that flag is not configurable** — it comes from
what the class is. An administrator setting it to false would not make deletion stop breaking
anything.

**A partial retention revision is refused.** It would leave unlisted classes at whatever the last
revision said, and a reader could not tell a decision from a leftover.

## The probe suite

`test_boundary_probes.py` signs in as a real member of workspace A and attacks workspace B, which
holds real records — a project, a run, an attempt with an admitted reader observation, and 99,999
metered tokens. Probing a nonexistent id proves only that nothing is nothing.

The central test collects **all twenty read routes** and asserts every one answers `404
RESOURCE_NOT_FOUND` and nothing else. A route answering 403, or a different code, or a longer
message, confirms the workspace exists and that something is in it. Collected into one test on
purpose: a route added without the shared refusal shows up as a diff on a list rather than as a
test nobody wrote.

The rest: the refusal body carries none of the other workspace's content; a forged `workspaceId` in
a body is refused rather than ignored; **my run plus their attempt** is refused (both identifiers
are individually legitimate, and a route validating each separately would answer); another
workspace's usage is not charged to mine; revoked membership and revoked sessions stop working on
the *next request*; and a canary sweep over 25 paths finds no session token, CSRF token, traceback,
`psycopg` string or filesystem path in any response.

## No independent review, and what I did instead

CodeRabbit reported **rate limited** on this pull request, as it did on module 24. I re-read the
diff against the defect classes the earlier reviews found, and three things were wrong:

**The concurrency limit was stored, displayed and never checked.** `max_concurrent_runs` had a
column, a value in the settings screen and no enforcement anywhere — precisely the dead guard this
codebase argues against. It is now checked inside the same locked transaction as the daily
allowance, *before* it, because it is the cheaper refusal and the one that resolves without anybody
doing anything. It raises its own exception with its own sentence: a daily limit is raised by an
administrator, and reporting this as "quota exhausted" would send an operator to change a number
that is not the problem.

**The usage event key was not namespaced by route.** A caller chooses their own idempotency key. A
key already used for some other operation would have read as a retry of this admission, and the run
would have been created without being charged. The key is now `POST /runs:<key>`.

**The settings screen holds a copy of the permission matrix.** `WORKSPACE_CONFIGURE` is owner-only,
and the copy is right — but a copy is a copy. There is now a test pinning it for `MAINTAINER`, the
role most likely to be added by mistake, since the server refuses either way and the visible cost of
being wrong is showing somebody a form whose submission always fails.

Four mutations confirm the three fixes and the role copy. This is not equivalent to an independent
review: I found the classes I already knew to look for.

## The operational consequence you should know about

**Every existing workspace now needs an entitlement before it can request a run.** A workspace
created before migration 0013 has none, and `POST /runs` answers `503 DEPENDENCY_UNAVAILABLE`
naming the missing configuration. That is deliberate and it is a breaking change: the alternative is
a default allowance, and a default allowance is a limit nobody chose. Module 18's test fixture was
updated to configure one, with a comment saying why.

## What is not done

The prompt's ten tasks are not ten deliverables of equal size, and six of them have no backend to
attach to.

- **Only run admission and concurrency are charged.** Actions, wall-clock seconds and model tokens
  have limits, columns, reporting and enforcement, and nothing records them — because nothing
  dispatches an action or calls a model. Those three limits are *enforceable and unenforced*, which
  is a different statement from enforced.
- ~~**No scoped deletion route.**~~ Built afterwards — see the addendum below.
- **No structured telemetry beyond `metrics.queue_health`.** No counters for reader or preflight
  failure, model failure, budget rejection or export integrity.
- **No rate limiting.** An authenticated member can issue unlimited requests to any read route. The
  budget bounds *work*, not requests.
- **No `ExecutionGrant` settings, no GitHub payload approval.** Grants are module 19's schema with
  no route; publication is module 20 and does not exist.
- **No dependency vulnerability scanning.** CI pins lockfiles and scans for committed secrets; there
  is no SCA tool.
- **No build-worker egress probe**, because there is no build worker. The claim that a build cannot
  reach the control plane or a metadata service is untested in both directions.
- **No privilege-revocation drill against a deployment**, because there is no deployment.
- **No external penetration test and no legal advice.** Every probe here was written by the person
  who wrote the code it probes, which is the weakest form of adversarial review there is. The threat
  model says so in its own section rather than in a footnote.

**The acceptance gate is partly met.** The declared deployment mode's tenant, authority, evidence
and budget boundaries withstand concrete probes through the real HTTP surface, and quota behaviour
is observable through the real service. The desktop boundary is not probed at all — it is one
dedicated local machine and a procedural agreement, and nothing prevents an operator enrolling the
computer they are sitting at. No bypass capable of granting unauthorized execution or a false PASS
was found; nothing was found because nothing executes.

**No actual screen reader** exercised the settings screen. Keyboard flows were driven by `userEvent`
in the unit tests and programmatically in the live browser — the same position as modules 21–24.

## Addendum — scoped deletion (FR-020), built after module 27

The gap recorded above is closed. `POST /runs/{id}/deletions` deletes named evidence classes for one
run or one attempt, and returns a report.

### The report is the deliverable, not the status code

FR-020 asks for deletion reaching "primary objects, derived views, exports, caches and supported
backups" and states the limit in the same sentence: "local downloaded copies cannot be remotely
recalled". A route answering `{"deleted": true}` would be the most dangerous endpoint in this
product — somebody would call it, see success, and tell a regulator the data was erased.

So every deletion returns a `retained` list, it is never empty, and it is assembled from actual state
rather than written as boilerplate. Live, against the real API and real MinIO:

```
POST deletions -> 201
  artifactsMarkedDeleted: 1 | objectsEnqueued: 1 | objectsPurged: 1 | objectsStillPresent: 0
  completenessInvalidated: True
  retained:
   - Audit metadata is retained: this deletion's own record, and a tombstone row for every artifact…
   - Backups taken in the last 35 day(s) still contain this evidence. A restore from one brings it…
   - The hash chain is intact and each cleared event keeps its digest…
   - No export of this run was ever built, so no bundle of it left this system by that route.
   - Human review records were not included…

bytes gone from the store: ArtifactStoreError
missing after: [{'kind': 'SPEECH_TRANSCRIPT', 'reason': 'BYTES_DELETED'}]
```

That last line is the acceptance clause: the run went from a complete evidence set to an incomplete
one. **Deletion costs the run its completeness claim rather than tidying it up.**

### Three decisions worth reading before changing this

**The event chain survives the payload.** `canonical_event` keeps `payload_digest` and
`previous_event_hash`; only `payload` is replaced. The chain still verifies end to end, so a reader
can prove no event was inserted or removed *and* see which ones they can no longer read. Deleting the
rows would break the chain at the deletion point and make every **undeleted** event after it
unverifiable — destroying the evidence somebody chose to keep as collateral damage of removing the
evidence they chose to delete.

**`ACTION_TRACE` and `EFFECT_RECEIPT` are not diagnostics.** The obvious mapping puts them with logs.
An action trace is the record of what was done to somebody's application and a receipt is proof an
effect occurred — both are what an ambiguous action is adjudicated from. Classing them as DIAGNOSTIC
would make deleting the proof of an OS action a routine cleanup that breaks no completeness claim,
which is the inference INV-09 exists to prevent.

**Two layers guard an unclassified kind.** A test reads the schema's own `CHECK` constraint and fails
if any artifact kind lacks a retention class; the deletion itself refuses rather than skipping if one
slips through. The cost of being wrong here is an artifact somebody believes was deleted.

### The test this closes

"No test of restoring a backup that predates a deletion" — now
`test_a_restore_from_a_backup_taken_before_a_deletion_brings_the_evidence_back`. It takes a real
`pg_dump` before the deletion, deletes, restores into a disposable database, and asserts the content
is back, the tombstone is not, and the restored database does not know a deletion happened. The
deletion worked. The restore worked. Both are correct, and together they are why the report names a
window in days instead of claiming the data is gone.

### Still not built

- **No UI.** The route and the `accessforge` client reach it; no screen does. A delete-evidence
  button is a decision about interface design for an irreversible operation, and the settings screen
  already states what deleting each class costs.
- **No workspace-wide erasure.** A different operation with a different blast radius; the one-button
  version is how somebody removes a year of evidence meaning to remove a week.
- **Nothing reaches a backup**, and nothing should: a deletion that could reach into backups could
  also be used to rewrite them. The delay is disclosed instead.

### The correction: the database commits before a single byte is touched

Review caught the first version calling the object store **inside** the caller's transaction. If an
earlier object deleted and a later statement raised, the transaction rolled back and the store could
not: bytes gone, artifact still `RETAINED`, no deletion record — and `missing_required_artifacts`
would report a **complete** evidence set for a run whose evidence no longer exists. That is the exact
failure this feature was built to prevent, reintroduced by the order of two calls.

Deletion is now two phases with a commit between them. `record_deletion` marks the artifacts, records
the deletion and enqueues every object key, touching no store; `purge_pending_objects` deletes the
bytes a committed deletion promised. Migration 0018 adds `evidence_object_purge` — a queue rather
than a flag on the artifact, because one artifact has two objects (the original and any redacted
view) and a key that fails needs its own error and its own retry count.

The inconsistency window now points the safe way: the database says deleted while some bytes may
still exist, nobody is told they are gone until they are, and a retry finishes the job. A store
outage is a delay, not a failed deletion — `purge_pending_objects` records the error on the row and
does not raise, because the database has already committed and telling the caller it failed would be
false.

**What the split made newly possible to get wrong.** Each of these is now guarded, and each guard is
confirmed by a mutation check that breaks it and names the test that fails:

- A purge asked about a deletion it cannot see found an empty queue and reported nothing pending —
  indistinguishable from success, with the bytes still in the store. This was not hypothetical: the
  first version of phase two ran in a FastAPI `BackgroundTask`, the request's transaction had not
  committed when it fired, and every count came back zero while the object sat in MinIO. The route
  now runs phase one on its own connection, which commits, and the purge raises rather than
  reporting an empty queue it cannot see.
- `still_pending` counted only the current pass's failures. A pass that removed every key it looked
  at still leaves a backlog when the queue is longer than its `limit`, and subtracting reported that
  backlog as zero. It is now read from the queue.
- `DeletionReport.retained` is composed rather than stored, so the pending-object line cannot be
  omitted by a caller that never ran a purge — the common case, and the one where its absence reads
  as a completed erasure.
- `with_purge` refuses an outcome measured for another deletion. A sweep counts every deletion's
  backlog, and quoting it would let one deletion report bytes as released on another's work.

The response says `artifactsMarkedDeleted`, `objectsPurged` and `objectsStillPresent`, which are
three different facts. The old `artifactBytesDeleted` conflated the first and the second.

### Independent review, and the finding it closed

A separate reviewer traced the correction against FR-020 and INV-02/06/09/15. It found no reachable
state where the database reports evidence as `RETAINED` while its bytes are gone — the invariant the
split exists to hold — and one Important finding, which was right:

**OPEN → FIXED WITH PROOF. The backlog had no retry path.** `purge_pending_objects` had exactly one
production caller, always scoped to the deletion created in that same request. A deletion left
incomplete by a store outage, or by a queue longer than one pass, could never be drained: requesting
the same deletion again marks nothing and enqueues nothing, because the artifacts are already
`DELETED` and the scope query skips them. So `objectsStillPresent` would have stayed above zero for
good, while the report said "a later pass finishes it" — describing a pass that did not exist.

Closed two ways. `purge_until_drained` loops until the queue stops shrinking, so a queue longer than
one pass is finished rather than stranded, and it stops on the first pass that removes nothing, so a
store outage costs one call rather than fifty. And `POST /runs/{runId}/deletions/{deletionId}/retry`
— owner-only, bound to the run in the URL — is the path the report now names by route. Live, after
an outage stranded a key:

```
OUTAGE: bytes still in MinIO: 37 bytes
  listing objectsStillPresent: 1
RETRY 200 {'objectsPurged': 1, 'objectsStillPresent': 0, 'keysFailed': []}
  the stranded bytes are gone from MinIO
```

**Also fixed, from a note the reviewer raised below its reporting bar.** Artifacts refused an
unmapped kind; events did not. `canonical_event.event_type` has no `CHECK` constraint, so an event
type added by a later migration without a retention class would not have been refused — it would
simply have been absent from the list of types to clear, and its payload would have survived a
deletion that reported success. It is now refused, symmetrically.

Three further observations were recorded and deliberately not acted on: `purge_pending_objects`
holds one transaction across up to 200 blocking store calls (a latency smell, not a correctness
bug); `evidence_object_purge.artifact_id` has no foreign key, though it is only ever written from a
row selected in the same transaction; and no test drives this route with an `Idempotency-Key`.

**1586 tests pass.** 52 `/v1` paths. Verified live against a real uvicorn process, PostgreSQL 17 and
MinIO: 201, five retained lines, the object refused on read-back, and a stranded key finished by the
retry route.
