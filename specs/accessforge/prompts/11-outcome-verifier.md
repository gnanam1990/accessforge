# Prompt 11 — Independent deterministic outcome verification

**Dependencies:** 06, 10. **Requirements:** FR-006, FR-007, FR-011, FR-023. **Release:** E0 and R1.

Read [SESSION-HEADER.md](SESSION-HEADER.md), [CONTRACTS.md](../CONTRACTS.md), TDD evaluator design and TEST-PLAN. This module is the outcome authority; an LLM narrative is input for diagnosis, never proof of success.

## Copy-paste prompt

```text
Implement AccessForge module 11 only.

Objective: Produce a bounded, explainable PASS/FAIL/INCONCLUSIVE outcome from the exact frozen contract and complete trusted evidence, independent of navigator confidence or repair intent.

Owns: packages/domain/evaluation/, trusted completion-observer adapters, finalization admission service and verifier tests. Do not modify journey assertions or reinterpret stale manifests to rescue a failed run.

Required inputs: Frozen module 06 assertions/fixture identity and module 10 integrity/completeness assembly. Module 02 defines the outcome truth table. Keep Run.status separate from Run.outcome and machine observations separate from human review.

Tasks:
1. Revalidate source, build, environment, runner, evaluator, model, journey, assertion and fixture identities against the sealed manifest. Reject missing or changed identities before considering favorable observations.
2. Consume module 10 completeness and producer-identity admission. Canonical/source gaps, missing required producer watermarks, stale leases, unauthorized observer records, missing artifacts, truncated speech or forbidden actions mean INCONCLUSIVE, even when the canonical ingestion chain is contiguous.
3. Evaluate frozen required assertions with explicit true/false/unknown values and evidence references. Preserve original observations alongside justified deterministic normalization; never let semantic model similarity decide the result alone.
4. Implement the independent fixture receipt observer with read-only scope and fresh fixture identity. Submit authenticated source records and closing watermark through the single sequencer; do not allocate canonical hashes. Observe actual backend state, not DOM text or navigator/supervisor-authored receipts.
5. Ensure observer answers and credentials cannot reach the navigator. Observer availability failures remain explicit unknowns; no success is inferred from request submission or frontend toast appearance.
6. Apply exact precedence: invalid/incomplete identity, preflight or evidence OR any UNKNOWN required assertion/completion condition → INCONCLUSIVE; otherwise any FALSE required assertion/completion condition → FAIL; otherwise all required conditions TRUE → PASS. UNKNOWN outranks simultaneous FALSE; preserve reason codes.
7. Admit final outcome through the journal transaction and reducer, binding evaluated evidence-set identity and evaluator version. Repeated evaluation of identical inputs is deterministic and cannot rewrite an immutable terminal record.
8. Publish structured supporting observations for findings: only a complete valid failed run can support REPRODUCED. A partial run may suggest a CANDIDATE without falsely confirming a defect.
9. Add independent offline/unit test fixtures not generated by the same code path as evaluation. Include known-valid, known-failed and incomplete actual-reader traces while clearly separating synthetic test data from real platform evidence.
10. Document exactly what a PASS establishes for the pinned journey/profile and what it does not establish: universal usability, all disabilities, legal compliance or correctness of an arbitrary external service.

Negative tests: Prior-fixture receipt, supervisor-forged observer record, missing producer tail, wrong phrase provenance, hidden-selector shortcut, simultaneous FALSE/UNKNOWN, false completion with all other assertions true, failure plus corrupt artifact, model PASS and reviewer override (INV-01 through INV-06, INV-11, INV-12, INV-16). Mutation-test UNKNOWN/evidence precedence, producer admission and required completion.

Acceptance: Real VoiceOver trace evaluation yields explainable results; tampering or loss changes the result to INCONCLUSIVE; a valid reproduced behavior failure becomes FAIL; a backend receipt alone never proves accessibility. Truth-table and mutation results are recorded.

Stop conditions: If a required observation is unreliable, keep it unknown and document the capability limit. Do not weaken an assertion, treat infrastructure failure as product failure or ask the model to choose a favorable result.

Handoff: Write docs/handoffs/11.md with evaluated run identities, reason coverage, observer isolation proof and interfaces ready for navigation, diagnosis and later baseline/candidate comparison.
```
